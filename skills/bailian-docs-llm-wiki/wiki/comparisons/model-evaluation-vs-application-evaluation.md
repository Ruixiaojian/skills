# 模型评估与应用评估对比

## 概述

百炼平台提供了两套独立的评测体系：**模型评测**和**应用评测**。两者虽然都旨在帮助开发者验证和优化 AI 系统的输出质量，但在评测对象、粒度、流程和适用阶段上存在显著差异。本文从多个关键维度对两者进行系统对比，帮助开发者根据实际需求选择合适的评测方案，或在不同开发阶段组合使用两种评测能力。

## 核心维度对比

| 维度 | 模型评测 | 应用评测 |
|------|----------|----------|
| **评测对象** | 单个或多个大语言模型（基础模型 / 调优模型） | 智能体应用、工作流应用（含 RAG、插件等完整链路） |
| **评测目标** | 模型选型、调优验证、风险预防 | 应用输出质量监控、端到端效果优化、上线前后持续回归 |
| **评测粒度** | 模型推理能力本身（不涉及外部工具链） | 应用全链路（含检索、重排、知识库、Prompt 工程等） |
| **评测方式** | 自定义评测（人工/自动）、基线评测 | 自动评测（旧版）、手动评测（旧版）、评测任务（新版，评估器 + 标签） |
| **数据输入格式** | 评测数据集或推理结果集（平台内管理） | `.xls`/`.xlsx`（对话分析）、`.jsonl`（知识问答）、自动生成模板、应用观测导入 |
| **评测输出** | 各维度通过率、评分明细 | 评测报告（含评分、归因分析、调优建议）、标签标注结果 |
| **支持模型** | 通义千问商业版/开源版、通义法睿、部分第三方模型 | 不直接限制模型，限制应用类型（智能体须已发布且配置知识库才能自动评测） |
| **评分机制** | 大模型分类/数值评估、规则字符串匹配、文本相似度算法（ROUGE-L、BLEU 等） | 1-5 分制（旧版自动）、较差/一般/较好（旧版手动）、评估器打分 + 标签标注（新版） |
| **归因能力** | 无内置归因（仅给出维度评分） | 自动归因（模型理解有误、重排不佳、检索无效、切片不完整、未获取知识） |
| **计费方式** | 参评模型推理 [Token](../concepts/token.md) 费 + 裁判模型 [Token](../concepts/token.md) 费 | 应用调用 [Token](../concepts/token.md) 费 + 评分模型 Token 费（新版评估器模型限时免费） |
| **区域限制** | 仅中国大陆版（北京地域） | 无特殊区域限制说明 |
| **版本状态** | 单一版本 | 新旧两版并存，可在界面切换 |

## 评测方式细项对比

| 对比项 | 模型评测 - 自定义评测 | 模型评测 - 基线评测 | 应用评测 - 自动评测（旧版） | 应用评测 - 新版评测任务 |
|--------|----------------------|--------------------|-----------------------------|------------------------|
| 是否需要人工参与 | 可选（人工评估 / 自动评估） | 否 | 否 | 可选（评估器自动 + 人工标签） |
| 评测集来源 | 用户准备 | 平台预置（C-Eval、CMMLU 等） | 基于知识库自动生成 或 复用已有 | 手动上传 / 应用观测导入 |
| 裁判模型 | 用户选择（推荐通义千问3-Max） | 系统内置 | 仅支持 qwen-max / qwen-plus | LLM 评估器（可选模型） |
| 多模型/多应用对比 | 支持多模型同时评测 | 支持 | 支持最多 8 个应用横向对比 | 单任务单应用 |
| 适合阶段 | 模型选型、调优后验证 | 调优后回归测试 | RAG 应用快速验证 | 应用迭代全生命周期 |

## 评估维度与评估器对比

| 对比项 | 模型评测评估维度 | 应用评测评估器（新版） |
|--------|-----------------|----------------------|
| 类型体系 | 大模型评估（分类型/数值型）、规则评估（字符串匹配/文本相似度）、人工评估 | LLM 评估器（语义理解）、Code 评估器（Python 脚本） |
| 数量限制 | 无明确限制 | 单任务最多 10 个评估器 |
| 变量注入 | 支持 `${prompt}`、`${completion}`、`${output}` | 通过参数映射关联评测集字段 |
| 创建方式 | 用户自定义 Prompt 模板 | 预置模板 / 自定义创建 / 基于历史任务创建 |
| 费用 | 裁判模型 Token 费 | LLM 评估器产生 Token 费（限时免费）；Code 评估器无额外费用 |

## 适用场景建议

### 推荐使用模型评测的场景

- **模型选型阶段**：在项目初期需要从多个候选模型中挑选最优基座模型时，模型评测可快速横向对比各模型在特定任务上的表现。
- **模型调优后的能力验证**：对模型进行 SFT/RLHF 等调优后，需要验证目标能力是否提升、通用能力是否退化，适合使用自定义评测 + 基线评测组合。
- **安全合规风险排查**：利用大模型评估（分类型）维度，批量检测模型输出中的政治敏感、违法犯罪、歧视偏见等风险。
- **纯模型推理能力基准测试**：不涉及外部工具调用、知识库检索等应用层逻辑，仅关注模型本身的语言理解、推理、代码生成等能力。

### 推荐使用应用评测的场景

- **RAG 应用质量验证**：当应用涉及知识库检索、文档切片、重排等环节时，应用评测的自动归因能力可精准定位问题来源（是检索问题还是模型问题）。
- **端到端应用效果监控**：关注的是最终用户体验而非单一模型能力时，应用评测能覆盖从输入到输出的完整链路。
- **工作流应用评测**：包含多步骤编排的工作流应用，仅新版应用评测支持。
- **持续迭代优化闭环**：应用上线后通过应用观测导入线上真实数据，持续回归验证，形成"发现问题→定位归因→优化→再评测"的闭环。
- **多维度人工标注**：需要领域专家从多个角度（分类、布尔值、数字、文本）对应用输出进行精细标注时，新版标签体系更为灵活。

### 组合使用建议

在完整的开发周期中，两种评测通常按以下顺序配合使用：

1. **模型评测**完成基座模型选型和调优验证 → 确定最优模型
2. 基于选定模型构建应用（配置 Prompt、知识库、工具等）
3. **应用评测**验证端到端应用效果 → 持续迭代优化

## 技术选型决策树

开发者可根据以下问题快速决策：

1. **你要评测的是"模型"还是"应用"？**
   - 如果是对比不同模型的裸推理能力 → **模型评测**
   - 如果是验证包含知识库/工具/工作流的完整应用 → **应用评测**

2. **你是否需要问题归因？**
   - 需要知道"是检索问题还是模型问题" → **应用评测**（自动归因）
   - 只需要知道"模型答对了还是答错了" → **模型评测**

3. **你的评测对象是否涉及工作流？**
   - 是 → **应用评测**（新版评测任务）
   - 否 → 根据其他条件判断

4. **你是否在做模型调优后的回归测试？**
   - 是，且关注通用能力是否退化 → **模型评测**（基线评测）
   - 是，且关注应用层面效果变化 → **应用评测**

5. **你是否需要使用标准榜单（C-Eval、CMMLU）？**
   - 是 → **模型评测**（基线评测）
   - 否 → 根据实际需求选择

## 总结

| | 模型评测 | 应用评测 |
|--|---------|----------|
| **核心价值** | 找到最好的模型 | 打造最好的应用 |
| **评测层次** | 模型层（Model Layer） | 应用层（Application Layer） |
| **关键优势** | 支持基线榜单、多模型横评、细粒度评分规则 | 端到端验证、自动归因、持续迭代闭环、工作流支持 |
| **主要局限** | 不覆盖应用全链路，无归因能力 | 自动评测依赖知识库配置，旧版/新版体系并存增加学习成本 |
