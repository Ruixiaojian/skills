# 模型评估与应用评估对比

## 概述

百炼平台提供了两套独立的评测体系——**模型评测**和**应用评测**，分别面向不同的评估目标和使用阶段。模型评测聚焦于大语言模型本身的能力验证与选型，而应用评测则面向基于模型构建的智能体应用和工作流应用，评估端到端的输出质量。

对于开发者而言，理解两者的定位差异和能力边界，有助于在项目不同阶段选择正确的评测手段，避免重复工作，构建从"选模型"到"优化应用"的完整质量保障链路。

---

## 核心维度对比

| 维度 | 模型评测 | 应用评测 |
|------|----------|----------|
| **评测对象** | 大语言模型（预置模型或调优后的模型） | 智能体应用、工作流应用（端到端） |
| **核心目标** | 模型选型、调优验证、风险预防 | 应用输出质量监控与持续优化 |
| **评测方式** | 自定义评测（人工/自动）、基线评测 | 自动评测（旧版）、手动评测（旧版）、评测任务（新版，评估器 + 标签标注） |
| **数据来源** | 评测数据集或推理结果集 | 知识库自动生成、手动上传、应用观测导入 |
| **评测集格式** | 统一的评测数据集 / 推理结果集 | 旧版：`.xls`/`.xlsx`（对话分析）、`.jsonl`（知识问答）；新版：按应用出入参自动生成模板或自定义表结构 |
| **自动评分机制** | 裁判模型（分类型/数值型）、规则评估（字符串匹配/文本相似度） | 旧版：大模型自动评分（1-5 分）；新版：LLM 评估器（语义理解）+ Code 评估器（Python 脚本规则） |
| **人工评估方式** | 评分员手动打标签（分类型） | 旧版：人工对比打分（较差/一般/较好）；新版：标签标注（分类/布尔值/数字/文本四种类型） |
| **支持的模型/应用** | 通义千问商业版/开源版、垂直领域模型、部分第三方模型 | 已发布的智能体应用和工作流应用（旧版自动评测要求已配置知识库） |
| **归因分析** | 无内置归因，需开发者自行分析 | 旧版自动评测提供 BadCase 归因（模型理解有误、重排不佳、检索无效、切片不完整、未获取知识） |
| **横向对比能力** | 支持多模型同时评测对比 | 旧版支持最多 8 个应用横向评测；新版按单任务执行 |
| **版本管理** | 无显式版本管理 | 评测集支持版本管理，需发布后方可使用 |
| **计费方式** | 评测过程中调用模型产生的 Token 费用按正常标准计费 | Token 费用按正常标准计费；新版评估器模型限时免费；独占资源部署的模型不额外收费 |
| **地域限制** | 仅适用于中国大陆版（北京地域） | 文档未注明特定地域限制 |
| **操作入口** | 百炼控制台 > 模型评测 | 百炼控制台 > 应用评测（新版/旧版可切换） |

## 评测能力详细对比

### 自动评估能力

| 能力 | 模型评测 | 应用评测 |
|------|----------|----------|
| 大模型语义评分 | ✅ 裁判模型分类型 / 数值型 | ✅ LLM 评估器 |
| 规则匹配 | ✅ 字符串匹配（相等/包含等） | ✅ Code 评估器（Python 脚本） |
| 文本相似度 | ✅ ROUGE-L、BLEU、Cosine、Fuzzy Match、Accuracy | ❌ 需通过 Code 评估器自行实现 |
| 基线回归测试 | ✅ 基于 C-Eval、CMMLU 等主流榜单 | ❌ 不支持 |
| 归因分析 | ❌ | ✅ 旧版自动评测提供五类归因 |
| 评估器数量限制 | 按维度配置，无显式上限 | 新版每个任务最多 10 个评估器 |

### 人工评估能力

| 能力 | 模型评测 | 应用评测 |
|------|----------|----------|
| 标签类型 | 分类型（如优秀/良好/不达标） | 分类、布尔值、数字、文本四种类型 |
| 标注灵活度 | 评分员按维度打标签 | 新版支持多种标签组合，可复用于应用观测 |
| 多人标注 | 建议多名评分员独立标注以验证一致性 | 文档未明确多人协作机制 |

## 适用场景建议

### 选择模型评测的场景

| 场景 | 说明 |
|------|------|
| **初期模型选型** | 项目启动阶段，需要在多个候选模型中快速筛选出最适合业务的模型 |
| **模型微调验证** | 完成模型调优后，需要对比调优前后的能力变化，确认调优效果 |
| **通用能力回归** | 领域调优后，需确保模型通用能力（如语言理解、推理）未明显退化 |
| **安全合规检查** | 上线前检测模型是否存在政治敏感、歧视偏见等风险输出 |
| **NL2SQL / Function Calling 精度测试** | 需要精确匹配或规则校验的结构化输出评估 |

### 选择应用评测的场景

| 场景 | 说明 |
|------|------|
| **RAG 应用质量评估** | 评估知识库检索 + 模型生成的端到端效果，定位检索、重排、切片等环节的问题 |
| **智能体应用上线前验收** | 对已发布的智能体应用进行系统化测试，确保回答质量达标 |
| **工作流应用评测** | 评估多步骤工作流的最终输出质量（仅新版支持） |
| **持续质量监控** | 知识库更新、Prompt 调整、模型替换后的回归验证 |
| **线上 BadCase 分析** | 从应用观测中导入真实对话数据，分析问题原因并闭环优化 |

## 技术选型参考

### 决策流程

```
项目启动
  │
  ├─ 需要选择底座模型？──→ 模型评测（多模型对比 + 基线评测）
  │
  ├─ 已完成模型调优，需验证效果？──→ 模型评测（自定义评测 + 基线评测）
  │
  ├─ 已构建智能体/工作流应用，需评估端到端效果？──→ 应用评测
  │
  ├─ 需要定位 RAG 链路中的具体问题（检索/重排/切片）？──→ 应用评测（旧版自动评测，含归因分析）
  │
  └─ 需要持续监控应用质量并闭环优化？──→ 应用评测（新版评测任务 + 应用观测联动）
```

### 组合使用建议

在实际项目中，模型评测和应用评测通常是**互补而非替代**关系，建议按以下阶段组合使用：

1. **模型选型阶段**：使用模型评测的自定义评测和基线评测，从候选模型中选出最优底座模型。
2. **模型调优阶段**：使用模型评测的自定义评测验证调优效果，同时用基线评测确保通用能力未退化。
3. **应用构建阶段**：使用应用评测的新版评测任务，评估智能体或工作流的端到端输出质量。
4. **应用上线阶段**：使用应用评测的旧版自动评测进行 RAG 全链路诊断，结合归因分析定位瓶颈。
5. **持续运营阶段**：定期使用应用评测进行回归测试，从应用观测导入线上数据进行 BadCase 分析和闭环优化。

### 关键注意事项

| 注意事项 | 说明 |
|----------|------|
| **地域限制** | 模型评测仅支持中国大陆版（北京地域），使用前请确认账号地域 |
| **应用状态要求** | 应用评测（旧版自动评测）要求应用已发布且已配置知识库，并开通应用观测 |
| **成本控制** | 两套评测体系均会产生 Token 费用；如已有推理结果，模型评测支持直接上传结果集以减少推理开销 |
| **新旧版本切换** | 应用评测存在新旧两个版本，新版功能更全面，建议优先使用新版评测任务 |
| **任务不可修改** | 两套体系的评测任务创建后配置均不可修改，如需调整须创建新任务 |
