# 模型监控与应用监控对比

## 概述

阿里云百炼平台提供两套互补的可观测能力：**模型监控**和**应用监控（应用观测）**。模型监控聚焦于模型调用层面的性能指标、[Token](../concepts/token.md) 消耗和用量管理；应用监控则聚焦于应用内部的调用链路追踪与端到端可观测性。两者的监控粒度、适用对象和数据获取方式存在显著差异。本文旨在帮助开发者根据实际需求选择合适的监控方案，或将两者结合使用以获得完整的可观测视图。

## 关键维度对比

| 对比维度 | 模型监控 | 应用监控（应用观测） |
|----------|----------|----------------------|
| **监控对象** | 模型调用（API 层面） | 应用内部调用链路（Trace/Span 层面） |
| **核心目标** | 追踪模型性能、[Token](../concepts/token.md) 消耗、成本控制 | 追踪应用端到端调用链、定位瓶颈节点 |
| **支持的目标类型** | 所有模型（含调优后的自定义模型） | 智能体应用、工作流应用、高代码应用 |
| **输入格式** | 无需额外配置，自动采集模型调用数据 | 需在控制台添加被观测应用，高代码应用需代码埋点 |
| **输出格式/数据形式** | 指标看板、PromQL 查询结果、告警通知 | Trace 链路图、Span 列表，支持导出 JSONL/EXCEL |
| **数据粒度** | 普通监控：小时级；高级监控：分钟级 | 分钟级 |
| **API/外部接入** | 支持 Prometheus HTTP API，可接入 Grafana | 暂无 API 接口 |
| **告警能力** | 支持（短信、邮件、电话、钉钉、企微、Webhook） | 不支持 |
| **日志/对话记录** | 支持查看历史对话（需开通审计日志和推理日志） | 自动记录输入 Prompt 及模型响应 |
| **链路追踪** | 不支持（仅单次调用维度） | 支持完整调用链追踪（CHAIN → AGENT → LLM → TOOL 等） |
| **筛选维度** | API-KEY、推理类型、时间范围、模型 | Request ID、Trace ID、Span ID、状态、延时、[Token](../concepts/token.md) 量、标签 |
| **核心指标** | RPM、TPM、首 Token 延时、调用时长、失败率、Token 消耗 | 调用次数、失败率、Token 总量、平均首 Token 耗时、平均调用时长 |
| **数据标注** | 不支持 | 支持自定义标签标注，可添加到评测集 |
| **计费方式** | 功能本身不收费；高级监控数据存储于私有 Prometheus 实例 | 功能本身不收费；数据存储依赖可观测链路 OpenTelemetry 服务（需付存储费） |
| **地域限制** | 高级监控：北京、新加坡、弗吉尼亚；告警：北京、新加坡；日志：北京、新加坡部分模型 | 无额外地域限制说明 |
| **数据保留** | 用量统计保留最近 30 天 | 监控统计最长 30 天 |
| **底层技术** | Prometheus | OpenTelemetry |

## 监控指标对比

| 指标类别 | 模型监控 | 应用监控 |
|----------|----------|----------|
| 调用次数 | ✅ `model_call_count` | ✅ 调用次数统计 |
| 失败率 | ✅ 失败次数、失败率、限流错误 | ✅ 失败次数与失败率 |
| 调用时长 | ✅ `model_call_duration` | ✅ 平均调用时长 |
| 首 Token 延时 | ✅ `model_first_token_duration` | ✅ 平均首 Token 耗时 |
| Token 消耗 | ✅ `model_usage`（按模型/空间汇总） | ✅ Token 总量（全部/输入/输出） |
| 内容安全 | ✅ 安全错误次数 | ✅ GUARDRAIL 节点可观测 |
| 成本指标 | ✅ 平均单次请求调用量 | ✅ 平均单次请求 Token 量 |
| 链路拓扑 | ❌ | ✅ 多层级 Span 展开 |
| 节点级耗时 | ❌ | ✅ 每个 Span 独立计时 |

## 适用场景建议

### 选择模型监控的场景

- **直接调用模型 API**：通过 SDK 或 HTTP 直接调用模型，未使用百炼的应用编排能力。
- **成本管控**：需要按模型维度追踪 Token 消耗、设置用量告警、管理免费额度。
- **运维告警**：需要对失败率、响应延迟等指标配置主动告警通知。
- **接入外部监控系统**：需要将监控数据接入 Grafana 或自建监控平台进行统一管理。
- **批量推理监控**：需要区分实时推理与批量推理的用量统计。
- **多模型对比**：需要横向对比不同模型的性能和成本表现。

### 选择应用监控的场景

- **应用调试与优化**：需要了解智能体或工作流内部各节点的执行顺序和耗时分布。
- **链路问题定位**：应用输出异常时，需要追踪具体是哪个节点（检索、模型推理、插件调用等）出了问题。
- **RAG 效果分析**：需要观察检索（RETRIEVER）、向量化（EMBEDDING）、重排（RERANKER）等节点的中间结果。
- **数据标注与评测**：需要对模型输出进行标注并导入评测集，形成数据闭环。
- **工作流节点级监控**：需要了解工作流中每个节点（API 调用、条件判断、脚本执行等）的执行情况。

### 建议同时使用的场景

- **生产环境全面可观测**：模型监控提供宏观指标告警，应用监控提供微观链路诊断，两者结合可实现从发现问题到定位根因的完整闭环。
- **性能优化迭代**：通过模型监控发现整体延迟升高，再通过应用监控定位到具体慢节点（如检索耗时过长或模型推理超时）。
- **成本优化**：模型监控追踪总体 Token 消耗趋势，应用监控分析单次调用中各环节的 Token 分布，找到优化空间。

## 技术选型参考

| 决策因素 | 推荐方案 |
|----------|----------|
| 仅通过 API 调用模型，无应用编排 | 模型监控 |
| 使用百炼智能体/工作流应用 | 应用监控（建议同时开启模型监控） |
| 需要接入 Grafana 或自建监控 | 模型监控（支持 Prometheus HTTP API） |
| 需要主动告警通知 | 模型监控（支持多通道告警） |
| 需要调用链路可视化 | 应用监控 |
| 需要导出数据做离线分析 | 应用监控（JSONL/EXCEL 导出） |
| 需要数据标注与评测闭环 | 应用监控 |
| 需要管理免费额度、控制成本 | 模型监控 |
| 高代码应用需要自定义上报 | 应用监控（配合 AgentScope-AI Tracing） |

## 总结

模型监控与应用监控并非互斥关系，而是分别覆盖了不同层次的可观测需求。模型监控是**基础设施层**的监控，关注的是"模型调用是否健康、成本是否可控"；应用监控是**应用逻辑层**的监控，关注的是"应用内部链路是否通畅、各节点表现是否符合预期"。对于使用百炼应用编排能力的开发者，建议同时启用两套监控，以获得从宏观到微观的完整可观测能力。
