# 模型监控与应用监控对比

## 概述

阿里云百炼平台提供了两套互补的可观测能力：**模型监控**（Model Monitoring）和**应用监控**（Application Monitoring，即"应用观测"）。模型监控侧重于对单次模型调用的性能指标、Token 消耗和用量进行追踪与告警；应用监控则关注应用层面的端到端调用链路追踪，帮助开发者理解智能体、工作流等复合应用的内部执行过程。

两者的监控粒度、数据来源和使用场景存在显著差异。本文从多个关键维度进行对比，帮助开发者在技术选型时选择合适的监控方案，或合理地将两者结合使用。

---

## 关键维度对比

| 维度 | 模型监控 | 应用监控（应用观测） |
|------|----------|----------------------|
| **监控对象** | 单个模型的每次 API 调用 | 智能体应用、工作流应用、高代码应用的完整调用链路 |
| **核心能力** | 调用指标监控、Token 消耗统计、用量管理、告警、Grafana 接入 | 调用链路追踪（Trace/Span）、节点级指标查看、数据标注与评测集管理 |
| **数据粒度** | 模型级别（按模型、API-KEY、推理类型等维度聚合） | 应用级别（按 Trace → Span 逐层展开，可深入到 LLM、检索、插件等子节点） |
| **支持的模型/应用类型** | 模型列表中的所有模型（含调优后自定义模型），高级监控限部分地域 | 智能体应用、工作流应用、高代码应用（不含 Assistant API 创建的智能体） |
| **监控指标** | Token 延时、调用时长、RPM、TPM、失败率、内容安全错误、平均单次调用量等四类指标（安全/成本/性能/错误） | 调用次数、失败次数与失败率、Token 总量（输入/输出）、平均首 Token 耗时、平均调用时长 |
| **日志能力** | 模型调用的输入/输出记录（需开通审计日志与推理日志），仅限北京和新加坡部分模型 | 自动追踪所有 Prompt 及响应数据，支持按 Request ID / Trace ID / Span ID 检索 |
| **告警能力** | 支持（成本、失败率、延迟等指标），通知方式含短信/邮件/电话/钉钉/企微/Webhook | 不支持独立告警配置 |
| **数据更新延迟** | 普通监控：小时级；高级监控：分钟级；用量统计：约 1 小时 | 分钟级 |
| **数据保留时长** | 用量统计页面保留最近 30 天 | 监控统计最长支持 30 天 |
| **API/外部集成** | 支持 Prometheus HTTP API，可接入 Grafana 或自建应用 | 暂无 API 接口 |
| **数据导出** | 通过 Prometheus API 获取指标数据；账单可通过费用中心导出 | 支持导出为 JSONL 或 EXCEL 格式 |
| **数据标注与评测** | 不支持 | 支持自定义标签标注（布尔值/分类/数字/文本），可批量添加到评测集 |
| **底层技术** | 私有 Prometheus 实例 | 可观测链路 OpenTelemetry 服务 |
| **计费方式** | 模型监控功能本身不额外收费，模型调用按各模型计费标准收费 | 应用观测功能本身不收费，数据存储依赖 OpenTelemetry 服务需支付存储费用 |
| **地域限制** | 普通监控无限制；高级监控限北京/新加坡/弗吉尼亚；告警限北京/新加坡；日志限北京/新加坡部分模型 | 文档未特别说明地域限制（依赖 OpenTelemetry 服务可用地域） |
| **开通方式** | 控制台模型监控配置中开启 | 需授权并开通 OpenTelemetry 服务，初始化 LogStore，然后在应用观测页面添加应用 |
| **筛选与过滤** | 按 API-KEY、推理类型、时间范围、模型等筛选 | 按状态、Span Name、输入/输出关键词、延时、Token 量、自定义标签等组合筛选 |

## 适用场景建议

### 选择模型监控的场景

- **直接调用模型 API 的应用**：通过 SDK 或 HTTP 直接调用百炼模型 API 的场景，需要监控每个模型的调用成功率、延迟和 Token 消耗。
- **成本管控优先**：需要追踪各模型的 Token 用量，管理免费额度，设置用量告警以防止超支。
- **多模型对比分析**：同时使用多个模型（如 qwen-plus 与 qwen-turbo），需要横向对比各模型的性能和成本。
- **需要主动告警**：对失败率、响应延迟、成本等指标设置阈值告警，第一时间响应异常。
- **需要接入外部监控系统**：已有 Grafana 或自建运维监控平台，希望通过 Prometheus API 将模型指标统一纳管。
- **批量推理场景**：需要区分实时推理与批量推理的用量和性能。

### 选择应用监控的场景

- **复合应用调试**：智能体或工作流应用涉及多个节点（模型推理、知识检索、插件调用、内容安全等），需要端到端追踪调用链路，定位具体环节的性能瓶颈或错误。
- **RAG 流程优化**：需要观测检索（Retriever）、向量化（Embedding）、重排（Reranker）、改写（Rewriter）等 RAG 各环节的实际执行情况和效果。
- **插件/工具调用调试**：智能体调用了多个插件，需要查看每个插件的输入输出和耗时。
- **数据标注与模型评测**：需要对线上真实调用数据进行质量标注，并将数据导入评测集用于后续模型或应用评测。
- **工作流节点级分析**：工作流中包含 API 调用、条件分支、脚本执行等节点，需要逐节点查看执行状态。

### 两者结合使用的场景

在生产环境中，建议**同时启用两套监控**以获得完整的可观测能力：

| 层级 | 使用的监控 | 目的 |
|------|-----------|------|
| **基础设施层** | 模型监控 | 追踪模型级别的 RPM/TPM、延迟、失败率，设置告警 |
| **应用层** | 应用监控 | 追踪端到端调用链路，排查应用逻辑问题 |
| **成本管理** | 模型监控 | 统一管理 Token 用量、免费额度和成本告警 |
| **质量优化** | 应用监控 | 标注线上数据，构建评测集，持续优化应用效果 |
| **运维大盘** | 模型监控（Prometheus API）+ 应用监控（控制台） | 将模型指标接入 Grafana 统一运维大盘，在控制台深入排查链路问题 |

## 技术选型参考

### 快速决策指引

```
是否使用了百炼的智能体/工作流/高代码应用？
├── 是 → 建议开启【应用监控】追踪调用链路
│     └── 同时建议开启【模型监控】管理用量和告警
└── 否（直接调用模型 API）
      └── 使用【模型监控】即可满足需求
```

### 关键差异总结

1. **监控视角不同**：模型监控是"模型视角"，关注单个模型的健康状态和资源消耗；应用监控是"应用视角"，关注一次用户请求在应用内部经历的完整链路。

2. **可编程性不同**：模型监控提供 Prometheus HTTP API，支持通过代码获取指标数据并接入第三方系统；应用监控目前暂无 API，只能通过控制台操作或导出文件。

3. **告警能力不同**：模型监控具备完善的告警机制（多等级、多渠道）；应用监控不提供独立的告警功能，如需告警需依赖模型监控或外部系统。

4. **数据运营能力不同**：应用监控提供数据标注和评测集管理能力，可将监控数据直接用于应用质量迭代；模型监控不具备此能力。

5. **开通成本不同**：模型监控开通较为简单（控制台配置即可）；应用监控需要额外开通 OpenTelemetry 服务并初始化存储，且可能产生存储费用。

### 注意事项

- 两套监控系统的数据**相互独立**，模型监控统计的 Token 消耗与应用监控中 LLM 节点展示的 Token 量来源不同，可能存在统计口径差异。
