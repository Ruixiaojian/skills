# 模型生命周期运维对比：部署、监控与评估

为帮助开发者在百炼平台上科学规划模型从上线到持续优化的全链路运维工作，本文系统对比三大核心能力模块——**模型部署（Deployment）**、**模型监控（Monitoring）** 和 **模型评估（Evaluation）**。三者分别对应模型生命周期的「交付阶段」「运行阶段」和「质量验证阶段」，共同构成生产级大模型服务的可观测性与可治理性基础。本对比聚焦技术实现差异、能力边界与协同关系，不替代各模块独立文档，而是提供横向选型视角，助力团队根据业务目标（如高并发交付、稳定性保障或效果迭代）快速匹配最优组合方案。

## 关键维度对比表

| 维度 | 模型部署（Deployment） | 模型监控（Monitoring） | 模型评估（Evaluation） |
|------|------------------------|-------------------------|--------------------------|
| **核心目标** | 将模型转化为稳定、可扩展、可计费的服务接口 | 实时观测服务健康度、性能瓶颈与成本消耗 | 量化验证模型能力表现，支撑选型、调优与质量回溯 |
| **输入格式** | JSON 部署配置（含 `model_name`, `plan`, `ptu_capacity`/`deploy_spec` 等）；模型需已导入并状态为“创建成功” | 调用请求（含 `model`, `prompt`, `max_tokens` 等）；监控数据自动采集，无需显式输入 | 评测数据集（CSV/JSONL，必含 `prompt` + `completion` 列）；维度配置（Prompt模板、裁判模型、阈值等） |
| **输出格式** | 部署实例 ID、API 端点（`/v1/chat/completions`）、服务元信息（如 `service_tier: "ptu-standard"`） | 多维指标（RPM/TPM/TTFT/失败率等）、调用日志（含输入/输出原文，*受限模型与地域*）、告警通知 | 评测报告（综合得分、通过率、维度分布图）、明细 CSV（每条样本评分）、排行榜排名 |
| **支持模型范围** | 全量预置模型 + LoRA 调优模型（PTU/MU 支持广，[Token](../concepts/token.md)用量仅限LoRA）；[多模态](../concepts/multimodal.md)/语音模型仅 MU 模式支持 | 所有可调用模型均支持基础用量统计；**推理日志、TPS、内容查看仅限部分快照模型（如 qwen3-max, qwen-plus）且限北京/新加坡/弗吉尼亚地域** | **仅文本生成类模型**（预置及LoRA调优模型）；[多模态](../concepts/multimodal.md)、语音模型**不支持**；基线评测**仅北京地域可用** |
| **API 端点** | `POST /api/v1/deployments`（创建部署）<br>`GET /api/v1/deployments/{id}`（查询状态） | `GET /api/v1/monitoring/metrics`（指标查询，需开通高级监控）<br>无公开日志拉取 API（日志仅控制台查看） | **无公开 API 或 SDK**；全部操作需通过控制台完成；自动化需对接 PAI Judge Model API 替代 |
| **计费方式** | 三模式并存：<br>• PTU：按预置吞吐额度（TPM）月付<br>• MU：按算力规格（MUx）+ 副本数（capacity）月付<br>• [Token](../concepts/token.md)用量：按实际调用 token 数实时计费 | • 普通监控：免费<br>• 高级监控（审计日志/推理日志/TPS/Grafana）：按日志量与指标采集频率计费（开通即启用） | • 被评测模型推理费（调用评测集产生）<br>• 裁判模型评分费（仅大模型评估维度产生）<br>• 规则评估与人工评估无额外费用 |
| **典型场景** | • 高并发客服机器人（PTU）<br>• 定制化金融问答服务（MU，需思考模式/RPM限流）<br>• A/B测试原型验证（[Token](../concepts/token.md)用量） | • 生产环境 SLA 巡检（失败率/TTFT告警）<br>• 成本异常归因（某API Key突增Token消耗）<br>• 故障根因分析（结合日志与TPS下降曲线） | • 新模型上线前效果验收（对比qwen3.7与glm-5.1）<br>• LoRA微调效果验证（基线 vs 微调后）<br>• 内容安全维度专项评测（人工+LLM双评） |
| **地域限制** | API 部署仅支持华北2（北京）；服务调用地域取决于部署时选择 | • 普通监控：全地域支持<br>• 高级监控（日志/TPS/告警/Grafana）：仅北京/新加坡/弗吉尼亚<br>• 上海仅支持普通监控 | • 自定义评测：全地域支持<br>• 基线评测：**仅北京地域可用** |
| **权限粒度** | 按业务空间（workspace）授权模型部署权限；子账号仅能部署已获权模型 | 数据隔离严格按业务空间；主账号可跨空间查看，子账号仅限所属空间 | 评测任务、维度、排行榜均绑定业务空间；权限继承自空间角色 |

## 各方案适用场景建议

### ✅ 推荐部署（Deployment）选型
- **选 PTU 模式**：当业务流量高度可预测（如每日固定时段订单处理）、对首Token延时（TTFT）敏感（<300ms）、需处理超长上下文（>64K tokens）且追求确定性成本时。适用于核心业务入口。
- **选 MU 模式**：当需要独占资源保障SLA、启用高级特性（如思考模式切换、动态RPM/TPM限流、PD分离计算）或部署[多模态](../concepts/multimodal.md)/语音专用模型时。适用于关键定制服务。
- **选 Token用量模式**：仅用于效果验证、灰度测试、低频调用场景（如内部工具、管理后台），**严禁用于生产流量承载**。成本不可控，无性能保障。

### ✅ 推荐监控（Monitoring）配置
- **必须开启普通监控**：所有生产环境模型的基础要求，用于宏观用量与失败率追踪。
- **强烈建议开通高级监控（北京/新/弗地域）**：若需分钟级故障响应（如TTFT突增告警）、精细化成本归因（单API Key Token消耗下钻）、或合规审计（原始输入/输出留存）。上海地域用户需迁移至支持地域以获得完整能力。
- **告警策略设计**：优先配置「失败率 > 5% 持续5分钟」与「Token消耗环比增长200%」两类规则，覆盖稳定性与成本双风险。

### ✅ 推荐评估（Evaluation）实践
- **上线前必做**：使用**自定义评测**，基于真实业务数据构建评测集，至少覆盖「回答准确性」「事实一致性」「内容安全性」三个核心维度，避免依赖基线数据集的泛化偏差。
- **调优后必验**：LoRA微调完成后，用同一评测集对比微调前后得分，重点关注维度短板（如安全性得分下降需检查训练数据过滤逻辑）。
- **规避常见陷阱**：不将1–3%的分数波动视为显著改进；不跨模型类型直接比较（如qwen3与glm-5.1的绝对分值无直接可比性）；人工评估需保证标注员一致性（建议≥3人交叉标注）。

## 技术选型参考（面向开发者）

作为开发者，在构建模型服务时，请按以下逻辑决策：

1. **先定交付形态，再配观测能力**  
   部署模式决定了服务底座能力（PTU/MU/Token），监控与评估必须在其约束下开展。例如：若选用 PTU 模式，则无法使用 MU 特有的 `enable_thinking` 参数，相应地，评估时也无需设计“思考过程合理性”维度。

2. **监控是部署的延伸，评估是监控的深化**  
   - 部署成功后，监控应立即启用（尤其高级监控），否则无法验证 PTU 缓存命中率或 MU 副本负载均衡效果；  
   - 当监控发现某模型 TTFT 持续偏高（>1s），应触发评估流程，用相同提示词集对比不同模型/参数配置，定位是模型本身瓶颈还是部署配置问题。

3. **地域与模型兼容性是硬约束**  
   若业务部署在华东1（上海），则无法使用推理日志与告警功能，此时需通过加强部署侧限流（MU 的 `rpm_limit`）与客户端重试机制弥补可观测性缺口；若需多模态评测，则当前平台不支持，需转向离线评估框架。

4. **成本需全局统筹**  
   PTU 的预付成本 + 监控高级功能费 + 评估中的裁判模型费用，可能远超 Token 用量模式的单次调用费。务必在架构设计初期进行 TCO（总拥有成本）测算，避免“部署省钱、监控烧钱、评估失控”的失衡局面。

> **最后提醒**：三者非孤立能力，而是闭环链条——部署提供服务入口，监控保障服务健康，评估驱动服务进化。建议在项目启动时同步规划三者的集成方案（如：将监控告警事件自动触发评估任务；将评估结果作为部署模式升级的决策依据），方能真正实现模型生命周期的智能化运维。
