# 应用监控与模型监控对比

阿里云百炼平台提供两套互补的可观测能力：**应用监控**（应用观测）聚焦于智能体/工作流/高代码应用的端到端调用链路追踪，而**模型监控**聚焦于模型调用层面的指标、Token 消耗、用量统计与告警。两者解决不同层次的问题——应用监控帮你"看清一次请求在应用内部如何流转"，模型监控帮你"看清模型被调用了多少次、花了多少 Token、表现是否稳定"。本文从技术选型角度给出对比，便于开发者按场景挑选合适的工具。

## 关键维度对比

| 维度 | 应用监控（Application Monitoring） | 模型监控（Model Monitoring） |
|------|-----------------------------------|-----------------------------|
| **监控对象** | 智能体应用、工作流应用、高代码应用 | 平台上调用的所有模型（含调优后的自定义模型） |
| **核心抽象** | Trace / Span / CHAIN 节点（基于 OpenTelemetry） | 模型调用记录 + Prometheus 指标时序 |
| **数据粒度** | 单次请求内部的子节点链路（LLM、RETRIEVER、TOOL、AGENT 等） | 单次调用的输入/输出 + 聚合指标（RPM、TPM、Token 总量等） |
| **典型查询入口** | Request ID / Trace ID / Span ID、时间范围、关键词、Span 名/状态/延时/Token 等 | 模型名、API-KEY、推理类型、时间范围 |
| **指标维度** | 调用次数、失败次数与失败率、Token 总量、平均单次 Token、首 Token 耗时、平均调用时长 | 四类指标：安全、成本、性能（调用时长/首 Token 延时/RPM/TPM）、错误（失败率/限流） |
| **数据更新频率** | 分钟级 | 普通监控小时级；高级监控分钟级；用量统计延迟约 1 小时 |
| **数据保留期** | 取决于 LogStore 配置 | 用量统计仅保留最近 **30 天**，更早数据需查账单 |
| **API 支持** | **暂无 API** | 高级监控支持 **Prometheus HTTP API**（可接入 Grafana / 自建应用） |
| **告警能力** | 不内置告警 | 支持告警规则（CRITICAL/ERROR/WARNING/INFO 四级，通过电话/短信/邮件/钉钉/企微/Webhook 通知） |
| **数据导出/再利用** | 支持导出 JSONL / EXCEL；支持标注；支持添加到评测集 | 通过 Prometheus API 拉取；用量数据可对账 |
| **地域限制** | 依赖 OpenTelemetry 服务，无显著地域限制 | 高级监控限北京/新加坡/弗吉尼亚；告警限北京/新加坡；日志功能仅限部分地域+部分模型 |
| **底层依赖** | 可观测链路 OpenTelemetry 服务（需授权 + 开通 + 初始化 LogStore） | 平台内置 Prometheus；日志需另开通审计日志和推理日志 |
| **计费方式** | 功能本身不收费，但 LogStore **存储费用**由 OpenTelemetry 服务侧收取 | 监控/告警/用量查看本身不收费；调用本身按模型计费，可配合"免费额度用完即停"控本 |
| **不支持/限制** | 暂无 API；不追踪长期记忆检索；TextRetriever/VectorRetriever 默认返回 100 切片不可调；高代码应用仅看到 FullCodeApp 触发，不追踪内部链路 | 不能按阿里云账号维度统计（仅业务空间）；日志/告警地域受限；用量数据非实时 |

## 适用场景建议

### 选择应用监控的场景

- **调试复杂智能体或工作流**：希望看到 Agent → LLM → Tool → Retriever 的全链路执行顺序与每一步的输入输出。
- **复盘单次失败请求**：拿到 Request ID 后想看具体在哪一步出错、延时卡在哪。
- **构建评测集**：要把线上 Span 数据批量沉淀为评测集（每个评测集最多 50 个字段映射）。
- **质量标注**：对线上 trace 打布尔/分类/数字/文本标签，反哺评测与回归。
- **关心 RAG 检索质量**：观察 RETRIEVER / RERANKER / REWRITER 节点的输入与输出。

### 选择模型监控的场景

- **关心成本与用量**：想知道某个模型在过去 30 天内消耗了多少 Token / 多少张图 / 多少秒。
- **生产可用性保障**：需要对失败率、限流、首 Token 延时、调用时长等设主动告警。
- **多模型对比与选型**：比较 qwen-max / qwen-plus / qwen-turbo 等在 RPM、TPM、失败率上的表现。
- **接入自建监控大盘**：希望把指标拉到 Grafana / Prometheus 体系内统一观测。
- **预算控制**：开启"免费额度用完即停"防止超额扣费。
- **审计 / 合规**：开通审计日志和推理日志保留输入/输出（限定地域和模型）。

### 同时使用两者的场景

绝大多数生产级智能体应用都应**同时**启用：

- 用**应用监控**做问题定位（哪一次请求、哪一个节点出问题）；
- 用**模型监控**做整体可用性 SLO（成本、性能、错误率的告警和趋势）；
- 应用监控发现某次 LLM Span 延时异常 → 跳到模型监控看该模型当时的 RPM/失败率是否整体劣化。

## 技术选型决策树

```
你的问题主要是？
├── "为什么这一次请求慢/错了" ────→ 应用监控（按 Trace ID 排查链路）
├── "这个模型最近表现如何" ──────→ 模型监控（指标 + 告警）
├── "本月花了多少钱 / 用了多少 Token" → 模型监控（用量统计）
├── "想把指标接到自家 Grafana" ──→ 模型监控（Prometheus HTTP API）
├── "想沉淀线上数据做评测" ──────→ 应用监控（导出 / 加到评测集 / 标注）
└── "想在出问题时自动通知" ──────→ 模型监控（告警 + 多通道通知）
```

## 关键差异提示

- **API 可用性**：当前只有模型监控开放了 Prometheus HTTP API，应用监控**暂无 API**，所有操作只能在控制台完成——如有自动化采集需求需优先考虑模型监控。
- **数据时效**：应用监控分钟级、模型监控的高级监控也是分钟级，但模型监控的"用量统计"延迟约 1 小时，做实时计费监控时需注意。
- **地域敏感**：模型监控的告警、日志等高阶能力对地域有较强限制；应用监控对地域不敏感但需要先开通 OpenTelemetry 服务。
- **数据保留**：模型监控的用量数据仅保留 30 天，长周期成本分析需配合账单；应用监控数据取决于 LogStore 的存储策略。
- **互补而非替代**：两者监控的对象不同——前者是"应用"，后者是"模型"。即便应用未启用应用监控，模型监控仍能记录到底层的模型调用；反之，应用监控里看到的 LLM Span 仅代表该应用内部触发的模型调用，无法替代模型监控对全平台模型调用的聚合视角。
