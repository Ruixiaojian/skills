# 知识库能力对比：Knowledge Base 与 Knowledge API

本文旨在帮助开发者清晰区分百炼平台中两类核心知识服务能力——**Knowledge Base（知识库）** 与 **Knowledge API（知识模块 API）**，明确其定位、能力边界、技术栈依赖及适用场景，避免在架构设计或集成选型中因概念混淆导致资源浪费、功能缺失或地域兼容性问题。二者虽均服务于 RAG 场景，但分属不同技术层级与产品形态：前者是面向应用构建者的**全托管式知识基础设施**，后者是面向系统集成者的**轻量级网关调用接口**。

---

## 关键维度对比

| 维度 | Knowledge Base（知识库） | Knowledge API（知识模块 API） |
|------|---------------------------|------------------------------|
| **本质定位** | 百炼平台原生的、可视化可配置的 RAG 数据增强层，需先创建并管理知识库实例 | DashScope 应用网关提供的标准化 HTTP 接口服务，不直接暴露知识库管理能力，依赖已部署的应用或索引 |
| **输入格式** | 支持多模态原始数据上传（PDF/Word/Excel/PPT/图片/音视频），支持元数据标注、标签过滤；查询时支持文本 Query + 可选历史对话上下文（多轮改写） | 仅支持纯文本 Query（`search`）或标准 Chat 消息数组（`chat`）；不支持直接上传文件或设置元数据过滤条件 |
| **输出格式** | • 检索模式：返回结构化切片列表（含 `content`、`score`、`source`、`metadata` 等字段）<br>• 问答模式：返回带引用溯源、拒答标识、流式生成结果的完整响应体（含 `citations`、`answer`、`status`） | • `/search`：返回 JSON 格式切片数组（字段较简，无 `citations` 或 `source` 原始路径）<br>• `/chat`：SSE 流式响应，按 `event: planning/tool_calling/generation` 分阶段推送，需客户端解析 `data` 字段 |
| **支持模型** | 显式支持多种向量模型（`text-embedding-v4`, `qwen3-vl-embedding`）、排序模型（`qwen3-rerank`, `qwen3-vl-rerank`）、路由模型（`qwen-plus`）；生成模型由用户在应用中自主选择 | **不暴露底层模型选择权**；检索阶段隐式使用平台默认向量+重排模型；问答阶段由绑定的 `app_id` 所指向的知识应用决定模型链路（不可覆盖） |
| **API 端点** | • 创建/管理：`POST /v1/knowledge_bases`（OpenAPI）<br>• 检索：`POST /v1/knowledge_bases/{kb_id}/retrieve`（SDK 封装）<br>• 问答：通过智能体/工作流触发，或调用 `/v1/apps/{app_id}/chat`（非本模块专属） | • 检索：`POST https://{workspaceId}.cn-beijing.maas.aliyuncs.com/api/v1/indices/knowledge/search`<br>• 问答：`POST https://{workspaceId}.cn-beijing.maas.aliyuncs.com/api/v2/apps/knowledge/chat` |
| **计费方式** | • **规格费用**：按知识库实例类型（标准版/旗舰版）按小时计费<br>• **模型费用**：向量嵌入（按文档页数/音视频时长）、Rerank（按初步召回总切片数）、生成（按 LLM [Token](../concepts/token.md)）分别计费<br>• 明确区分“召回”与“返回”成本（Rerank 按 TopK 计费，非最终数量） | • **无独立知识库规格费**；费用归属至所调用的 `app_id` 对应知识应用（其背后知识库已单独计费）<br>• 接口调用本身**不额外计费**，但每次请求会触发底层知识库的向量检索与 Rerank，产生对应模型费用<br>• 实际成本取决于所绑定应用的配置（如是否启用 Rerank、TopK 设置等） |
| **地域支持** | **严格限定华北2（北京）地域**；控制台、API、SDK 均不支持其他地域（新加坡、法兰克福等国际站点暂未开放） | 同样**仅支持华北2（北京）地域**；Base URL 中强制包含 `.cn-beijing.`，且 `workspaceId` 必须为北京地域创建的业务空间 |
| **典型场景** | • 需要长期维护私有知识资产（如企业 SOP、产品手册、客服话术库）<br>• 要求细粒度参数调优（相似度阈值、TopK、多知识库权重、多轮改写）<br>• 需结合智能体/工作流实现复杂业务逻辑（如拒答策略、引用高亮、多源混排）<br>• 多模态内容（图文/音视频）检索与理解 | • 已有外部系统（如 CRM、工单系统）需快速接入语义检索能力<br>• 无需管理知识库生命周期，仅需“即查即用”式问答调用<br>• 客户端具备 SSE 流式解析能力，追求低延迟端到端响应<br>• 知识应用已发布且稳定，仅需标准化 API 对接 |

## 适用场景建议

### ✅ 选择 **Knowledge Base（知识库）** 当：
- 你正在从零构建一个垂直领域智能助手（如法律咨询机器人、医疗知识助理），需要**自主上传、清洗、标注、版本化管理**私有知识；
- 业务对检索精度敏感，需反复调试 `相似度阈值`、`TopK`、`Rerank 模型` 等参数以平衡效果与成本；
- 需要支持**图片问答、音视频片段检索**等多模态能力；
- 期望在控制台完成可视化配置，并与百炼智能体/工作流深度集成（如添加拒答规则、自定义提示词、引用溯源展示）；
- 团队具备一定 RAG 工程经验，愿意承担知识库生命周期管理（更新、重建索引、监控日志）。

### ✅ 选择 **Knowledge API** 当：
- 你已有成熟的知识应用（`app_id` 已发布），只需将其能力**以标准 HTTP 接口形式嵌入现有业务系统**（如嵌入客服坐席系统、内部 OA 页面）；
- 开发团队偏好 REST/SSE 调用范式，**不愿引入百炼 SDK 或 OpenAPI 复杂依赖**；
- 场景简单，仅需“输入问题 → 返回答案”，无需干预检索过程（如不关心切片来源、不需修改元数据过滤逻辑）；
- 需要与前端流式渲染强耦合（如实时打字效果、思考过程可视化），且能处理 `planning/tool_calling/generation` 三阶段事件；
- 系统已统一使用 `workspaceId + API Key` 鉴权体系，希望复用该安全模型。

### ⚠️ 不推荐混合使用的典型误区：
- 试图用 Knowledge API 直接管理知识库（如上传文档、设置权重）——它**不具备知识库 CRUD 能力**；
- 在 Knowledge Base 控制台创建知识库后，却未发布对应知识应用（`app_id`），直接调用 `/chat` 接口——将返回 `404 Not Found`；
- 期望 Knowledge API 支持 `filter` 元数据过滤或自定义 Rerank 模型——当前 v1/v2 接口**未开放此类参数**，需通过 Knowledge Base 配置实现。

## 技术选型参考（面向开发者）

| 决策因素 | Knowledge Base | Knowledge API |
|----------|----------------|----------------|
| **开发门槛** | 中高：需理解 RAG pipeline（索引→检索→重排→生成）、配置多参数、处理 SLS 日志 | 低：仅需构造 HTTP 请求、解析 JSON/SSE，无模型/索引概念负担 |
| **运维负担** | 高：需关注知识库状态、配额（QPS/RCU）、索引重建、地域一致性、日志审计 | 低：无实例管理，故障定位聚焦于 `app_id` 状态与网关响应码（4xx/5xx） |
| **灵活性** | ★★★★★：完全掌控数据源、模型链路、召回策略、生成逻辑 | ★★☆☆☆：能力封装在 `app_id` 内，变更需重新发布应用 |
| **扩展性** | 支持多知识库路由、混排、权重调度，适合大型知识中台架构 | 单次调用绑定单一 `app_id`，跨知识源需多次请求或前置聚合 |
| **调试友好性** | 控制台提供召回详情页、切片溯源、耗时分解，便于效果归因 | 仅返回最终结果或切片列表，缺乏中间 pipeline 可视化（需依赖应用层日志） |
| **合规与审计** | 支持 SLS 日志投递，字段完整（`pipeline_id`, `latency`, `response_code`, `chunk_count`） | 日志粒度较粗，主要记录网关层指标（HTTP 状态、响应时长），无底层检索细节 |

> **总结建议**：  
> - **MVP 快速验证 → 优先 Knowledge API**（5 分钟接入，验证 RAG 效果）；  
> - **生产级知识中枢 → 必选 Knowledge Base**（保障可控性、可观测性、多模态与长期演进）；  
> - **混合架构推荐路径**：用 Knowledge Base 构建和治理知识资产 → 发布为标准化知识应用（`app_id`）→ 对外通过 Knowledge API 提供服务。此模式兼顾工程严谨性与集成简洁性。
