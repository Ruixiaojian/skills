# 知识接入方案对比：Knowledge API、知识库与数据连接

为帮助开发者在百炼平台中高效构建 RAG 应用，本文系统对比三种核心知识接入能力：**Knowledge API（应用网关层语义服务）**、**知识库（端到端 RAG 能力中心）** 和 **数据连接（外部数据源统一接入通道）**。三者定位不同、能力互补，但常被混淆使用。本对比旨在厘清技术边界、明确适用阶段，支撑从原型验证到生产部署的全周期选型决策。

---

## 关键维度对比

| 维度 | Knowledge API | 知识库 | 数据连接 |
|------|----------------|----------|------------|
| **本质定位** | 应用网关层的 *轻量级知识调用接口*，不管理知识生命周期，仅消费已建好的索引 | 百炼平台原生的 *RAG 全栈能力中心*，覆盖知识上传、向量化、检索、重排、生成、评测与运维 | *外部数据源的标准化接入层*，聚焦安全纳管与按需拉取，本身不提供向量化或问答能力 |
| **输入格式** | 纯文本 query（JSON body），如 `{"query": "什么是百炼平台？"}`；不支持文件/数据库原始数据直接输入 | 支持[多模态](../concepts/multimodal.md)原始数据：PDF/DOCX/Markdown/Excel/CSV/图片/音视频（自动解析+切分+向量化）；也支持已有向量索引 ID 引用 | 结构化/非结构化原始数据源：OSS 文件、MySQL/PostgreSQL 表、语雀知识库、PolarDB-X、本地上传文件等；**不执行向量化**，仅提供访问通道 |
| **输出格式** | • 检索：返回 JSON 数组，含 `text`、`score`、`metadata` 字段的 chunk 列表<br>• 问答：SSE 流式响应，含 `planning` → `tool_calling` → `generation` 三阶段事件 | • 检索：JSON 格式 chunk 列表（含溯源引用、置信度、来源页码/时间戳）<br>• 问答：富文本流式响应（支持图文混排、引用高亮、拒答标识），可配置是否返回原始 chunk | 无统一输出格式。由下游工具决定：<br>• `searchFile` / `searchTable` → 返回匹配的文件/记录片段（纯文本或结构化 JSON）<br>• `executeSQL` → 返回 SQL 查询结果集（JSON Array）<br>• `searchOSSFile` → 返回 OSS 对象元信息及预签名 URL |
| **支持模型** | 仅限百炼平台内建的 **知识问答专用流程引擎**（非通用 LLM 接口）；不开放模型切换 | 全面支持：<br>• 预置模型：Qwen 系列（Qwen3/Qwen2.5/Qwen2/Long/Max/Turbo/Coder/Deep-Research/VL-Max/OCR 等）<br>• 第三方模型：DeepSeek-R1/V3.1、Llama3.1、Yi-Large 等<br>• 自定义微调模型 | **不绑定任何大模型**。作为数据工具被智能体或工作流调用，模型选择完全由上层应用决定（如使用 Qwen3 或 DeepSeek-R1 执行最终生成） |
| **API 端点** | • 检索：`POST https://{workspaceId}.cn-beijing.maas.aliyuncs.com/api/v1/indices/knowledge/search`<br>• 问答：`POST https://{workspaceId}.cn-beijing.maas.aliyuncs.com/api/v2/apps/knowledge/chat` | • SDK/API：`bailian.KnowledgeBase.retrieve()` / `.qa()`<br>• 控制台集成：通过「知识库节点」拖入工作流或「+ 文档知识库」关联智能体 | • 工具调用：在智能体提示词或工作流节点中声明工具名（如 `searchTable`），运行时由平台注入连接器 ID 与参数<br>• 无独立 REST 端点；所有调用均经 `bailian.Tools.invoke()` 或工作流引擎路由 |
| **计费方式** | • 按调用次数计费（QPS 级别）<br>• 无存储/RCU/向量化费用<br>• 默认限流 25 QPS，超限返回 `429` | • 多维度计费：<br> ✓ 向量化处理（按文档页数/音视频时长）<br> ✓ 检索调用（RCU × 使用时长，旗舰版）或固定 QPS（标准版）<br> ✓ 重排服务（按召回切片数量 × [Token](../concepts/token.md)）<br> ✓ 生成 [Token](../concepts/token.md)（按所选模型计费） | • 无直接知识服务费用<br>• 仅产生基础资源消耗：<br> ✓ 文件托管（限时免费，超限后按 OSS 计费）<br> ✓ DTS 同步流量（若启用定时同步）<br> ✓ 下游模型调用费用（由实际使用的 LLM 产生） |
| **典型场景** | • 快速验证语义检索效果（无需建知识库）<br>• 在已有向量索引基础上做低延迟联合检索<br>• 构建轻量级问答代理（如客服机器人预检模块） | • 构建企业级垂直领域问答系统（如产品手册问答、合同审查助手）<br>• 多源异构知识融合（文档+表格+图片+音视频）<br>• 需要引用溯源、多轮改写、动态标签过滤的生产级 RAG 应用 | • 实时对接业务数据库（如查询订单状态、用户画像）<br>• 动态同步协作平台内容（语雀/钉钉/飞书知识库）<br>• 安全纳管私有 OSS 中的敏感资料，按需检索而非全量导入 |

## 适用场景建议

### ✅ 选择 **Knowledge API** 当：
- 你已通过 OpenAPI（如 `CreateIndex`）完成知识库创建与向量化，仅需快速调用其检索/问答能力；
- 项目处于 PoC 阶段，希望绕过知识库控制台操作，直接通过代码集成验证语义能力；
- 需要与其他系统（如自研前端、第三方调度平台）解耦，以标准 HTTP 接口暴露知识服务能力；
- 对延迟敏感，且无需[多模态](../concepts/multimodal.md)支持、引用溯源、拒答策略等高级 RAG 特性。

### ✅ 选择 **知识库** 当：
- 你需要开箱即用的完整 RAG 流水线（上传→解析→切分→向量化→检索→重排→生成→评测）；
- 数据源包含 PDF/Word/图片/音视频等复杂格式，且要求视觉理解、语音转文字、剧情解析等[多模态](../concepts/multimodal.md)能力；
- 应用需满足企业级合规要求：如引用溯源（标注答案出处）、元数据过滤（按部门/密级/时间筛选）、防泄漏策略（屏蔽敏感字段）；
- 团队缺乏向量数据库运维经验，希望由百炼统一托管索引生命周期与性能调优（RCU 弹性伸缩、自动重排优化）。

### ✅ 选择 **数据连接** 当：
- 你的知识源是实时变化的业务系统（如 MySQL 订单库、PostgreSQL 用户表），无法或不应离线导入；
- 需要将多个外部知识源（OSS 文档 + 语雀规范 + 钉钉会议纪要）统一纳管，并在同一个智能体中按需调用；
- 数据敏感度高，明确要求“原始数据不出域”，仅允许按查询条件拉取片段，禁止平台侧持久化副本；
- 已有成熟的数据治理流程（如 DMS 数据目录、OSS 生命周期策略），希望复用现有基础设施而非重建知识库。

## 技术选型参考（面向开发者）

| 选型目标 | 推荐方案 | 关键理由 |
|----------|-----------|-----------|
| **最小可行集成（MVP）** | Knowledge API | 无需创建知识库、无需配置连接器，只需 workspaceId + API Key 即可发起首次检索，5 分钟完成 Hello World |
| **文档密集型问答（如政策解读、技术手册）** | 知识库 | 原生支持 PDF/DOCX 智能解析、章节识别、公式保留；提供 `相似度阈值`/`TopK`/`标签过滤` 等精细化检索控制，效果优于通用向量检索 |
| **实时业务数据问答（如“查张三最近 3 笔订单”）** | 数据连接（MySQL/PostgreSQL） | 直接执行 SQL，毫秒级返回结构化结果；避免将动态数据反复导入知识库导致时效性滞后与存储冗余 |
| **混合知识场景（内部文档 + 外部数据库 + 协作平台）** | **知识库 + 数据连接 组合使用** | 在同一智能体中：用知识库处理静态 PDF/图片，用数据连接查询实时订单，用语雀连接器同步最新 SOP —— 平台自动编排工具调用顺序与上下文融合 |
| **成本敏感型轻量应用** | Knowledge API（低频） 或 数据连接（只读） | Knowledge API 无存储成本；数据连接无向量化/重排费用；二者均避免知识库 RCU 与向量化预处理开销 |
| **需要自主可控向量基础设施** | 不推荐任一方案，应选用 OpenAPI + 自建向量库 | Knowledge API 和知识库均依赖百炼托管索引；数据连接不提供向量化。如需完全掌控 embedding 模型、索引类型（HNSW/IVF）、更新策略，请直接调用 `CreateIndex` 等 OpenAPI 接口 |

> 💡 **最佳实践提示**：  
> - **不要用 Knowledge API 替代知识库**：前者是“能力调用”，后者是“能力构建”。Knowledge API 无法创建/更新/管理知识库，必须前置依赖 OpenAPI 完成索引建设。  
> - **数据连接 ≠ 知识库替代品**：它不提供语义检索，`searchTable` 仅支持关键词匹配或简单 SQL；复杂语义问题仍需先将结构化数据导入知识库并启用向量化。  
> - **三者可协同**：典型架构为——数据连接同步原始数据 → 知识库完成向量化与索引构建 → Knowledge API 或 SDK 对外提供标准化服务接口。
