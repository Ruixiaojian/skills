# [长期记忆](../concepts/long-term-memory.md)与记忆库方案对比

为帮助开发者清晰理解百炼平台中两类核心[长期记忆](../concepts/long-term-memory.md)能力的定位、能力边界与技术差异，本文对 **“[长期记忆](../concepts/long-term-memory.md)（新）”**（`long-term-memory-new`）与 **“记忆库”**（`memory-library`）进行系统性对比分析。二者虽同属平台级长期记忆基础设施，但在设计目标、架构演进、功能覆盖及适用场景上存在显著差异。本对比旨在支撑技术选型决策，避免因概念混淆导致集成成本上升或能力误用。

## 关键维度对比

| 维度 | 长期记忆（新） | 记忆库 |
|------|----------------|---------|
| **定位与目标** | 面向结构化用户状态持久化的**新一代统一记忆底座**，强调规则引擎与向量检索融合、多项目隔离、画像-记忆协同建模 | 百炼平台早期推出的**通用长期记忆组件**，以开箱即用、快速集成为核心，侧重跨会话上下文保持与 Agent 框架友好性 |
| **输入格式** | `messages`（最多 50 条对话，一问一答计 2 条）或 `custom_content`（≤512 字符），二者互斥必填；优先使用 `custom_content` | 同样支持 `messages`（无明确条数限制说明，但实际受服务端截断逻辑约束）或 `custom_content`（≤512 字符），二选一；支持同时传入 `profile_schema` 触发画像提取 |
| **输出格式** | 所有接口返回标准 JSON，含 `request_id`；`AddMemory` 额外返回 `event` 字段（`ADD`/`UPDATE`/`DELETE`）；`SearchMemory` 返回带 `score` 的语义匹配结果列表 | 接口返回结构一致，但 `GetUserProfile` 提供**独立结构化画像对象**（非记忆片段）；`SearchMemory` 返回字段含 `minScore`（0–100 整数，文档注明需归一化为 [0,1] 使用） |
| **支持模型/能力** | ✅ 自动记忆提取（基于对话/文本）<br>✅ 语义搜索（`SearchMemory`）、分页列表（`ListMemory`）、增删改查（`Add/Delete/UpdateMemory`）<br>✅ 用户画像模板定义（`CreateProfileSchema`）与关联使用<br>✅ 多规则集支持（通过 `project_id` 或 `project_ids` 切换）<br>❌ **不提供 `GetUserProfile` 接口** | ✅ 全套 CRUD + `GetUserProfile`<br>✅ 双模式提取：`Pro`（启用 Rerank，¥0.03/次）与 `Lite`（无 Rerank，¥0.018/次）<br>✅ 明确支持画像提取与获取（`profile_schema` + `GetUserProfile`）<br>✅ 控制台可配置记忆片段**有效期**（7/30/180 天或永不过期）<br>✅ OpenClaw 插件深度集成（`autoCapture`/`autoRecall`） |
| **API 端点** | 统一 Base URL：<br>`https://dashscope.aliyuncs.com/api/v2/apps/memory/`<br>全部 10 个接口均在此路径下，方法与路径见 API 参考文档 | 同一 Base URL：<br>`https://dashscope.aliyuncs.com/api/v2/apps/memory/`<br>接口集合与“长期记忆（新）”高度重合，但部分接口行为存在细节差异（如 `UpdateMemory` 在“记忆库”中 SDK 已封装，而“长期记忆（新）”中 Python SDK 尚未支持） |
| **计费方式** | 按调用次数计费，**未在文档中明确区分 Pro/Lite 模式**；默认按基础抽取能力计费（参考记忆库 Lite 价格，实际以控制台或账单为准） | 明确区分两种抽取模式：<br>• `Lite` 模式：¥0.018/次（基础提取）<br>• `Pro` 模式：¥0.03/次（启用 Rerank，提升召回质量）<br>画像提取、搜索、管理类操作单独计费（具体单价见控制台定价页） |
| **典型场景** | • 需要严格按业务域划分记忆规则（如电商客服 vs 金融顾问使用不同 `project_id`）<br>• 要求记忆与画像强绑定且共享同一规则引擎<br>• 构建高定制化智能体，需精细控制记忆生成逻辑与生命周期策略 | • 快速接入 OpenClaw 等主流 Agent 框架，追求零配置启动<br>• 需要同时管理非结构化记忆片段 + 结构化用户画像，并频繁调用 `GetUserProfile`<br>• 对记忆时效性有明确要求（如会员权益信息仅保留 30 天），依赖控制台可视化配置过期策略<br>• 希望通过 `Pro` 模式获得更高精度的语义召回结果 |

## 各方案的适用场景建议

### ✅ 推荐选用「长期记忆（新）」的场景：
- **多租户/多业务线隔离需求强烈**：例如 SaaS 平台为不同客户分配独立 `project_id`，确保记忆提取逻辑完全隔离。
- **记忆与画像深度耦合建模**：业务要求用户画像字段（如“偏好品类”）必须由同一套规则从对话中同步提取，并与对应记忆片段自动关联。
- **自研 Agent 框架且需细粒度控制**：开发者已构建自有运行时，希望直接调用 REST API 并自主管理 `project_ids`、`memory_library_id` 等上下文参数，规避插件抽象层。

### ✅ 推荐选用「记忆库」的场景：
- **快速落地 Agent 应用**：尤其使用 OpenClaw、LangChain 等框架，可直接安装官方插件，5 分钟完成 `autoCapture`/`autoRecall` 集成。
- **需要结构化画像与非结构化记忆并行管理**：例如客服机器人既要记住用户投诉事件（记忆片段），又要持续更新“问题类型”“满意度评分”等画像字段，并通过 `GetUserProfile` 实时获取。
- **对召回质量敏感且愿为精度付费**：业务场景（如医疗咨询、法律问答）要求高相关性结果，可选用 `Pro` 模式提升 `SearchMemory` 准确率。
- **依赖可视化运维能力**：团队需在控制台实时调试检索效果、调整规则权重、配置记忆有效期，而非仅依赖 API 调试。

## 面向开发者的选型参考

| 选型考量 | 建议动作 |
|----------|----------|
| **是否已使用 OpenClaw？** | → 优先选「记忆库」：官方插件成熟稳定，`autoRecall` 自动注入上下文，大幅降低集成复杂度。 |
| **是否需 `GetUserProfile` 接口？** | → 必须选「记忆库」：该接口未在「长期记忆（新）」文档中定义，是记忆库独有能力。 |
| **是否需配置记忆有效期？** | → 选「记忆库」：控制台提供 7/30/180 天或永不过期选项；「长期记忆（新）」当前无自动过期机制，需业务侧自行实现定时清理。 |
| **是否需 Rerank 提升搜索质量？** | → 选「记忆库」并启用 `Pro` 模式；「长期记忆（新）」未声明 Rerank 支持。 |
| **是否需 Python SDK 完整封装（含 `UpdateMemory`）？** | → 选「记忆库」：其 Python SDK 已完整支持所有接口；「长期记忆（新）」的 `UpdateMemory` 当前需手写 REST 调用。 |
| **是否需跨项目复用同一套规则？** | → 选「长期记忆（新）」：支持 `project_ids` 数组传参，便于 A/B 测试或多场景联合推理。 |
| **是否追求最小学习成本上线？** | → 选「记忆库」：默认库开箱即用，控制台提供调试沙盒，文档示例覆盖全链路。 |

> **重要提醒**：二者 API 端点相同、鉴权方式一致（`Authorization: Bearer $DASHSCOPE_API_KEY`），**底层存储与向量引擎共享**。技术选型本质是选择不同的能力组合与抽象层级，而非互斥的技术栈。生产环境建议：初期用「记忆库」快速验证，规模化后根据规则隔离、画像协同等需求，平滑迁移至「长期记忆（新）」。
