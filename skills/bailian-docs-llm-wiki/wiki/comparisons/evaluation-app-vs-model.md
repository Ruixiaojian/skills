# 应用评测与模型评测对比

阿里云百炼平台同时提供「应用评测」与「模型评测」两条评测链路。前者面向已经落地的智能体应用 / 工作流应用，关注端到端业务效果；后者面向基座模型与调优后模型，关注模型能力本身的客观打分。两者的入口、数据格式、评分机制与典型用户都不同，开发者在做技术选型时需要先想清楚「我要回答的问题是『这个应用够不够好用』，还是『这个模型够不够强』」，再决定走哪条路径。

本文从评测对象、数据形态、评分机制、计费方式等关键维度做横向对比，为团队在百炼平台上落地评测体系提供选型参考。

## 关键维度对比

| 对比维度 | 应用评测 | 模型评测 |
| --- | --- | --- |
| 评测对象 | 智能体应用、工作流应用（端到端） | 大语言模型本体（基座 + 调优后版本） |
| 入口 | 控制台「应用评测」（旧版 + 新版两套形态） | 控制台「模型评测 → 评测任务」 |
| 评测模式 | 旧版：自动评测 + 手动评测；新版：评测集 + 评测任务 + 评估器 + 标签 | 自定义评测 + 基线评测 |
| 数据集类型 | 旧版：对话分析（xlsx）、知识问答（jsonl）；新版：智能体 / 工作流 / 自定义 | 评测数据集（Excel：Prompt + Completion）、推理结果集（Excel：Prompt + Completion + Output） |
| 数据格式约束 | xlsx / jsonl，单次最多 10 文件，单文件 ≤ 20MB；新版类型创建后不可改 | Excel；仅支持「评测集」类数据，不支持训练集；推理结果集必须含 Output 列 |
| 数据来源 | 手动上传 + 应用观测直接拉真实数据 | 自备 Excel 数据集；基线评测使用系统预置标准数据集 |
| 评分机制 | 新版评估器：预置模板 / 自定义 LLM / 自定义 Code（Python 3.10）/ 基于历史评测任务抽象；旧版自动评测：大模型 1-5 分 | 评测维度 5 种：大模型评估-数值型、大模型评估-分类型、规则评估-文本相似度、规则评估-字符串匹配、人工评估-分类型 |
| 评分尺度 | 评估器自定义评分范围 + 通过阈值；评分 ≥ 阈值判 Pass | 默认 0~5，可改；大模型评估类需配「裁判模型 + 评分器模板 + 评分范围 + 通过阈值」 |
| 人工标注 | 标签管理：分类 / 布尔 / 数字 / 文本四类；支持快速标注模式 | 人工评估-分类型维度；评测时可选「人工评测」分发给评分员 |
| 支持的被评测对象 | 已发布的智能体应用 / 工作流应用；旧版自动评测要求已配置知识库 + 已开通应用观测 | 自定义评测：千问 QwQ/Max/Plus/Turbo/Coder/Math、Qwen 开源、通义法睿、第三方文本生成模型及其调优版本；基线评测：仅调优后的模型 |
| 计费方式 | 评测任务发起即扣 Token，按所选模型价格计费；评估器为 LLM 时产生 Token 费用，Code 评估器零费用；旧版自动评测中间步骤即使任务失败也计入用量 | 大模型评估类按裁判模型 Token 计费；规则评估几乎零成本；System Prompt 触发的被评测模型推理费用单独归属；推理结果集模式可省去推理费用 |
| 结果呈现 | 数据明细（评分 + 标签）+ 指标统计（综合得分 + 标签统计） | 数据明细（每条 Prompt/Completion/Output/各维度得分）+ 指标统计（综合得分、通过率、完成量等），基线评测额外提供分学科明细、能力雷达图、与 GPT-4/Claude 等业界模型横向对比 |
| 排行榜 | 不涉及 | 创建评测任务时可勾选「参与排行榜」 |
| 关键限制 | 评测任务一旦创建除标签外不可修改；评测集发布后被引用不可删除；新旧版同名功能数据不互通 | 数据集只能是「评测集」类型；基线评测仅支持调优后的模型；灰色无「申请」按钮的模型不可用 |
| 典型场景 | 智能体回答质量回归、知识库 BadCase 分析、工作流端到端验证、上线前人工标注校验 | 模型选型横向对比、调优前后效果量化、能力雷达汇报、定期能力监控 |

## 适用场景建议

### 选择应用评测

- 你已经基于百炼搭建了**智能体应用**或**工作流应用**，需要在上线前后衡量端到端业务效果。
- 关心**知识库召回 + 模型回答 + 业务规则**的整体表现，而不仅仅是模型本身。
- 需要把**人工标注**沉淀为长期可复用的评测体系，配合标签管理做多维度归因分析。
- 想从**应用观测**直接抽取真实线上对话作为评测样本，建立"线上数据回流 → 评测 → 改进"的闭环。
- 评估器需要**混合使用 LLM 评分 + 代码精确校验**（例如「相关性（LLM）+ 格式校验（Code）」），需要 Code 评估器的确定性。

### 选择模型评测

- 你的目标是**回答模型本身够不够强**，例如在多个候选模型（千问、GPT、Claude 等）间做横向选型决策。
- 正在做**模型调优**，需要量化调优前后的分数提升（例如 75 → 85），并对比公开基线（C-Eval、MMLU、GSM8K、BBH 等）。
- 需要向团队 / 管理层用**综合得分、通过率、雷达图、排行榜**等指标做能力汇报。
- 需要建立**定期监控机制**（如每月评测），追踪模型在固定数据集上的表现趋势。
- 已经积累了 Excel 形态的标注数据，且希望以**评测数据集（自动推理后打分）或推理结果集（直接读 Output）**两种成本档自由切换。

### 两者结合使用

实际工程中，应用评测与模型评测并不互斥，推荐组合使用：

1. **模型评测**先把候选模型/调优结果筛出来，确定底座；
2. **应用评测**在确定底座后，验证整套智能体/工作流应用的端到端效果，并通过标签持续沉淀业务化标准；
3. 上线后用应用评测的**应用观测拉数据 + 快速标注**持续监控，模型层若有重大更新（重新调优、换底座），再回到模型评测做基线复核。

## 技术选型决策清单

开发者在做选型时，可按以下顺序自检：

- **评测对象是什么？** 智能体 / 工作流 → 应用评测；裸模型 / 调优模型 → 模型评测。
- **数据来源是什么？** 来自线上应用对话 → 应用评测（可直拉应用观测）；来自整理好的 Excel 测试集 → 两者都可，但模型评测的 Excel 格式更标准化。
- **评分逻辑是规则还是模型？** 需要 Python 自定义规则 → 应用评测的 Code 评估器；需要快速搭起 AI 打分 → 两者都支持 LLM 评分，应用评测的评估器可独立复用，模型评测的评分器随评测维度绑定。
- **是否需要排行榜 / 公开基线对比？** 需要 → 模型评测（基线评测 + 排行榜）；不需要 → 应用评测足够。
- **预算约束如何？** 应用评测中 Code 评估器零费用、LLM 评估器按 Token 计费；模型评测的规则评估几乎零成本，大模型评估类按裁判模型 Token 计费，推理结果集模式可节省被评测模型的推理费用。
- **是否需要团队协同标注？** 需要长期沉淀人工经验 → 应用评测的「标签管理 + 快速标注」更体系化；一次性人工评分 → 模型评测的人工评估-分类型维度即可满足。

> **提示**：应用评测的新旧版本之间「评测集」「评测任务」等同名概念数据结构不互通，团队内务必统一版本；模型评测的基线评测严格依赖「已完成调优部署」，未调优的账户在模型下拉中会看到空列表，请先完成调优流程再创建任务。
