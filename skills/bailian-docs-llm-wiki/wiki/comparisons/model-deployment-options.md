# 模型部署方案对比：高并发推理、模型压缩与生产部署

为帮助开发者在百炼平台上高效完成从模型优化到规模化服务的全链路落地，本文系统对比三类核心部署能力：**高并发推理加速（TPM 预留 & 快速模式）**、**模型压缩（量化部署）** 和 **生产级模型服务化（PTU / MU / Token 用量）**。三者定位不同——高并发推理聚焦**运行时性能保障与响应速度优化**，模型压缩解决**资源效率与成本压缩问题**，而生产部署则定义**服务形态、计费模型与SLA边界**。本对比旨在厘清技术边界、明确适用阶段，并为不同业务场景下的技术选型提供可操作的决策依据。

---

## 关键维度对比表

| 维度 | 高并发推理（TPM 预留） | 高并发推理（快速模式） | 模型压缩 | 生产部署（PTU 模式） | 生产部署（MU 模式） | 生产部署（Token 用量） |
|------|------------------------|--------------------------|-----------|------------------------|------------------------|--------------------------|
| **核心目标** | 保障专属吞吐容量，规避公共资源争抢导致的限流 | 提升单请求解码速度（TPS），降低输出延迟 | 降低模型部署资源规格（MU），节省推理成本 | 提供稳定、可预估的高并发服务能力（输入/输出双维度保障） | 提供独占计算资源、可定制性能指标（如首 token 延迟）的私有化部署 | 轻量验证用按量计费，适用于调优后模型的效果测试与低频调用 |
| **输入格式** | 与标准 API 完全一致（OpenAI / Anthropic / DashScope 兼容） | 同标准 API，但**必须使用专属域名**（`{workspace_id}.{region}.maas.aliyuncs.com/compatible-mode/v1`） | 不直接处理输入；压缩是模型构建环节，输出为新模型 ID | 同标准 API；支持长输入（最高 1M token），含阶梯系数与前缀缓存逻辑 | 同标准 API；输入长度受 `max_context_length` 严格限制，超限报错 | 同标准 API；仅支持 LoRA 微调模型，无长输入或缓存优化 |
| **输出格式** | 同标准 API；无额外字段 | 同标准 API，但流式响应中新增 `delta.reasoning_content` 字段需单独解析 | 不改变输出语义；压缩后模型输出与原模型一致（精度损失除外） | 标准响应 + `service_tier="ptu-standard"` + `provisioned_tokens`（含阶梯/缓存折算） + `cached_tokens` | 标准响应；`service_tier` 未返回或为 `"default"`；支持 `enable_thinking` 等定制字段 | 同 MU 模式；无 PTU 特有字段（如 `cached_tokens`） |
| **支持模型** | Qwen3.x、GLM-5.x、DeepSeek-v4、Kimi-K2.6 等主流预置模型（控制台实时列表为准） | **仅 `glm-5.2-fast-preview`**（Preview 阶段，不支持 Qwen/GLM 其他版本） | **仅百炼平台微调产出的自定义模型**（如 `qwen3.5-flash-xxx`），不支持基础模型或第三方模型 | Qwen、GLM、DeepSeek 等主流预置模型（如 `qwen3.8-Max`, `glm-5.2`, `deepseek-v4-pro`） | LoRA 微调模型 + 部分大模型（如 `qwen3.6-35b-a3b`, `glm-5.1`） | **仅 LoRA 微调模型**（`plan=lora`），不支持全参微调模型 |
| **API 端点** | 与标准 API **完全一致**（无需更换域名或 header） | **必须使用专属域名**：<br>`https://{workspace_id}.{region}.maas.aliyuncs.com/compatible-mode/v1` | 无独立 API；压缩后模型通过标准部署接口（如 `/api/v1/deployments`）发布并调用 | 与标准 API **完全一致**（同一 endpoint） | 与标准 API **完全一致**（同一 endpoint） | 与标准 API **完全一致**（同一 endpoint） |
| **计费方式** | **预付费为主**：按 kTPM/天；溢出部分按 token 计费 | **纯按 token 计费**（与标准 API 一致）；支持缓存折扣（¥4/百万 tokens） | **压缩任务免费（限时）**；压缩后模型部署按 MU 规格**实时计费** | **预付费**：按 `input_tpm` / `output_tpm` 配额包月/包日；溢出可配置「自动转按量」或「严格限流（429）」 | **按 MU 规格 + 副本数实时计费**（如 `MU1 × 2`） | **纯按 token 计费**（仅限 LoRA 模型） |
| **典型场景** | 大促期间客服机器人、金融风控批量分析、企业知识库高并发问答 | AI 编程助手实时补全、Agent 多步推理中对输出速度敏感的步骤 | 将微调后的业务模型从 `MU8×1` 压缩至 `MU2×1`，降低 75% 推理成本 | 日均百万级请求的 SaaS 应用、需保障 P99 延迟 <500ms 的企业服务后台 | 需定制首 token 延迟 SLA（如 <200ms）、或要求 PD 分离架构的私有化部署 | LoRA 模型上线前 A/B 测试、小流量灰度验证、内部工具轻量调用 |

## 各方案适用场景建议

### ✅ 推荐组合策略（面向生产落地）
| 业务需求 | 推荐方案组合 | 说明 |
|----------|--------------|------|
| **高并发 + 低延迟 + 成本可控** | `PTU 模式` + `模型压缩` | 先对微调模型做量化压缩（如 `qwen3.5-flash-xxx → qwen3.5-flash-xxx-int4`），再以压缩后模型创建 PTU 部署，兼顾吞吐保障与 MU 成本下降。 |
| **极致首 token 响应 + 稳定资源隔离** | `MU 模式` + `TPM 预留`（同模型） | 在 MU 部署基础上叠加 TPM 预留，既获得独占资源与首 token 可控性，又避免高峰期因共享池波动导致的排队延迟。 |
| **快速验证新模型能力 + 低成本试跑** | `Token 用量模式` → `PTU/MU` | 先用 Token 模式快速验证 LoRA 模型效果；确认达标后，再迁移至 PTU（稳态高流量）或 MU（定制化强）正式部署。 |
| **AI Agent 多步推理流水线** | `快速模式`（关键步骤） + `PTU`（主干服务） | 对 Agent 中耗时最长的「代码生成」「规划分解」等步骤启用 `glm-5.2-fast-preview` 加速；其余步骤走 PTU 保障整体链路稳定性。 |

### ⚠️ 明确不推荐的误用场景
- ❌ **将 `glm-5.2-fast-preview` 用于 TPM 预留**：二者正交，快速模式模型 ID 不支持预留配额。  
- ❌ **对非微调模型（如 `qwen3-max`）执行模型压缩**：平台强制校验来源，仅接受状态为“成功”的微调任务产出模型。  
- ❌ **在 Token 用量模式下部署全参微调模型或尝试长输入**：该模式仅支持 LoRA 模型，且无长输入支持能力，超限将直接失败。  
- ❌ **在华北2以外地域使用模型压缩**：当前仅支持北京地域，跨地域部署需同步迁移工作空间。

## 技术选型参考指南（面向开发者）

请按以下流程进行决策：

1. **先确定模型来源与类型**  
   → 若为**百炼微调产出的 LoRA 模型**：可进入模型压缩 → 再选择 PTU/MU 部署；也可跳过压缩，直选 Token 用量（验证）→ PTU（生产）。  
   → 若为**预置大模型（Qwen/GLM/DeepSeek）**：不可压缩，直接选择高并发推理（TPM/快速模式）或生产部署（PTU/MU）。  

2. **再评估流量特征与 SLA 要求**  
   - ✅ **流量可预估 + 高并发 + 需长输入/缓存** → 优先选 **PTU 模式**（搭配阶梯系数与前缀缓存）。  
   - ✅ **流量突发性强 + 无法容忍 429** → 必须叠加 **TPM 预留**（即使已用 PTU）。  
   - ✅ **单请求输出速度敏感（如编程补全）** → 查看是否支持 `glm-5.2-fast-preview`，是则启用 **快速模式**（注意域名切换）。  
   - ✅ **需首 token <200ms + 独占资源 + 自定义上下文长度** → 选 **MU 模式**，并开启 `enable_thinking` 与 PD 分离。  

3. **最后确认成本与运维约束**  
   - 长期稳定服务 → 避免依赖 Preview 功能（如快速模式），优先选用 PTU 或 MU。  
   - 成本敏感型业务 → 强烈建议对微调模型执行**多模板量化对比**（利用免费期），选择精度损失可控下的最小 MU 规格。  
   - 运维能力有限 → 优先 PTU（自动扩缩容、溢出兜底），避免手动管理 MU 副本与生命周期。  

> 💡 **一句话总结**：  
> **TPM 预留 = “资源保底”**，**快速模式 = “速度加速”**，**模型压缩 = “规格瘦身”**，**PTU = “稳态高并发服务”**，**MU = “定制化私有服务”**，**Token 用量 = “轻量验证入口”**。  
> 三类能力并非互斥，而是分层协作——压缩优化模型本体，部署定义服务形态，高并发推理强化运行时体验。合理组合，方能实现性能、成本与可靠性的最优平衡。
