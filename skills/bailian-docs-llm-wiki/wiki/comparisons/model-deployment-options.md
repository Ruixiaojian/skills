# [模型部署](../concepts/model-deployment.md)方式对比：高并发推理、生产部署与压缩优化

为帮助开发者在百炼平台上高效、稳定、经济地落地大模型应用，本文系统对比三种关键[模型部署](../concepts/model-deployment.md)能力：**高并发推理（TPM 预留 & 快速模式）**、**生产部署（Model Production）** 和 **压缩优化（Model Compression）**。三者定位不同、技术路径各异，分别解决**流量确定性保障**、**定制化模型服务化**和**资源成本优化**三大核心问题。本对比旨在厘清能力边界、明确适用条件，避免因选型错配导致 SLA 不达标、上线延迟或成本失控。

---

## 关键维度对比表

| 维度 | 高并发推理（TPM 预留） | 高并发推理（快速模式） | 生产部署（Model Production） | 压缩优化（Model Compression） |
|------|------------------------|--------------------------|------------------------------|-------------------------------|
| **核心目标** | 保障确定性吞吐与稳定性（SLA 可承诺） | 提升单请求输出速度与响应实时性（低延迟交互） | 将微调/自定义模型发布为可调用的在线服务 | 降低微调[模型部署](../concepts/model-deployment.md)资源消耗与单位推理成本 |
| **输入格式** | 标准 OpenAI 兼容格式（`messages`, `temperature`, `stream` 等） | 同 TPM 预留；流式响应新增 `reasoning_content` 字段 | 标准 OpenAI 兼容格式；微调训练需 JSONL 指令数据集 | 无直接 API 输入；仅作为部署前的离线处理环节 |
| **输出格式** | 标准 OpenAI `chat.completions` 响应（含 `usage`） | 同标准格式 + `reasoning_content`（结构化推理中间态） | 标准 OpenAI `chat.completions` 响应（含 `model`, `usage`） | 无运行时输出；产出为新模型 ID（如 `ft-abc123-int4`），供后续部署使用 |
| **支持模型** | 千问、GLM、DeepSeek、Kimi 等主流基座模型（华北2/新加坡），按模型版本精确匹配 | 当前仅 `glm-5.2-fast-preview`（Preview 阶段） | ✅ 百炼原生基座模型微调产物（`ft-xxx`）<br>✅ 已导入的 ONNX / Hugging Face 格式自定义模型<br>❌ 不支持基础模型直连部署 | ✅ 仅限百炼平台内完成的微调模型（`ft-xxx`）<br>❌ 不支持基础模型、第三方上传模型、OSS 模型 |
| **API 端点** | 使用专属 model code（如 `qwen3.7-max-20260520-tpm-xxxxx`）+ 标准百炼 API 域名 | 使用 `glm-5.2-fast-preview` + workspace 专属域名（`https://{workspace_id}.cn-beijing.maas.aliyuncs.com/...`） | 使用部署生成的 endpoint（`https://<endpoint_name>.api.bailian.aliyun.com/v1/chat/completions`） | 无独立 API；通过控制台创建任务，结果模型 ID 可用于 `model production` 部署 |
| **计费方式** | ✅ 按天预付费购买专属 `input_tpm` / `output_tpm`（单位：kTPM）<br>✅ 支持缓存折扣（如 GLM-5.2 缓存命中按 25% 折算）<br>❌ 无请求级用量计费 | ✅ 按实际 token 用量计费（同标准模型）<br>❌ 无容量预购费用<br>❌ 不支持缓存折扣（文档未声明，价格表无差异） | ✅ 按部署实例规格（MU 数量 × 运行时长）计费<br>✅ 微调任务按 GPU 小时计费<br>❌ 无 TPM 或 token 用量附加费 | ✅ 压缩任务当前限时免费<br>✅ 压缩后模型部署仍按 MU 规格计费（显著低于原模型）<br>❌ 无 token 或 TPM 关联计费 |
| **典型场景** | 企业客服机器人（日均 500 万 tokens，峰值稳定）、金融风控实时决策、SaaS 平台核心 API SLA 要求 ≥99.95% | 编程助手实时补全、Agent 多步推理链首跳响应、低延迟对话前端（用户感知延迟 <800ms） | 行业垂类问答机器人（基于私域数据微调）、内部知识库智能助手、需长期迭代的定制模型服务 | 微调模型上线后成本敏感型业务（如百万 DAU 应用）、边缘/轻量级部署需求、预算受限但需保留微调效果的场景 |

## 适用场景建议

### ✅ 推荐选择 **TPM 预留** 当：
- 业务流量可预估（如日均/峰值 TPM 波动 ≤20%），且不可接受任何限流（HTTP 429）；
- SLA 合约要求严格（如 P99 延迟 ≤1.5s，可用性 ≥99.95%）；
- 需要利用缓存折扣或长文本阶梯系数优化成本（如大量 64K+ 输入）；
- 场景对吞吐稳定性优先于单请求极致延迟（如批量摘要、报告生成）。

### ⚠️ 谨慎选择 **快速模式** 当：
- 场景对首 token 延迟极度敏感（如代码 IDE 实时补全），且能容忍排队不确定性；
- 流量存在突发尖峰但整体均值较低，不愿预付 TPM 成本；
- **仅限 Preview 验证阶段使用**：不建议用于生产环境长期依赖，因模型 ID、性能、计费可能变更。

### ✅ 推荐选择 **生产部署（Model Production）** 当：
- 模型需基于私有数据微调（如客服话术、法律条文、医疗指南）；
- 需要完全自主控制模型生命周期（训练 → 部署 → 版本灰度 → 下线）；
- 服务需独立 endpoint 域名、独立鉴权、独立监控与告警（区别于共享模型池）；
- 需部署非百炼原生模型（如自研 ONNX 模型、Hugging Face 社区模型）。

### ✅ 推荐选择 **压缩优化** 当：
- 已完成微调并验证效果达标，但部署成本过高（如 `MU1*2` → `MU8*1` 节省 56%）；
- 业务对推理精度容忍小幅下降（量化后 BLEU/ROUGE 下降 ≤1.5%，人工评估无明显劣化）；
- 部署地域为华北2（北京），且模型状态为“训练成功”；
- **必须前置条件**：压缩是部署前的可选步骤，不可替代部署本身。

## 开发者技术选型参考

| 选型目标 | 推荐路径 | 关键动作提醒 |
|----------|----------|--------------|
| **保障高并发稳定性** | ✅ TPM 预留 + 标准模型部署 | • 用 [TPM 容量计算器](../../raw/model-user-guide/model-high-speed-inference/tpm-reservation.md) 精确估算输入/输出 TPM<br>• 替换 API 请求中的 `model` 为专属 code，勿混用标准模型 ID<br>• 设置客户端重试逻辑（429 错误需退避重试） |
| **追求极致响应速度** | ⚠️ 快速模式（Preview）→ 后续升级至 TPM 预留 | • 仅用于原型验证，上线前务必迁移至 TPM 预留或生产部署<br>• 解析流式响应时必须处理 `reasoning_content` 字段<br>• 监控排队时长（`x-queue-time-ms` 响应头），超 2s 需告警 |
| **交付定制化模型服务** | ✅ Model Production 全流程 | • 微调数据集必须为 JSONL 格式，每行含 `messages` 字段<br>• 部署 endpoint name 需全局唯一，建议含业务标识（如 `hr-bot-v2`）<br>• 微调失败时检查 `error_code`（如 `INVALID_TRAINING_FILE`），非仅看 HTTP 状态码 |
| **降低长期运营成本** | ✅ 压缩优化 + 生产部署 | • 压缩前确保源模型状态为“成功”，且已发布校准数据集<br>• 优先选择 MU 规格适配的模板（如 `MU8*1`），避免过度压缩导致精度崩塌<br>• 压缩后模型 ID 可直接用于 `/v1/deployments` 创建新部署，无需重新微调 |

> **重要提醒**：  
> - **三者非互斥，而是协同组合**：例如，可先对微调模型执行压缩，再将其部署为生产服务，最后为该服务配置 TPM 预留以保障高并发；  
> - **快速模式 ≠ TPM 预留**：前者是调度优化，后者是资源预留，二者原理不同，不可互相替代；  
> - **所有能力均依赖工作空间开通模型服务及对应 API Key 权限**，请提前在控制台完成权限配置。
