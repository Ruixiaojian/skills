# 模型部署方式对比：高并发推理、压缩、生产化部署

为帮助开发者在百炼平台上高效、稳定、经济地将大模型投入实际业务，本文系统对比三种关键部署能力：**高并发推理（TPM 预留 & 快速模式）**、**模型压缩（量化优化）** 和 **生产化部署（Model Production）**。三者并非互斥替代关系，而是面向不同阶段、不同目标的协同能力——高并发推理聚焦**运行时性能保障**，模型压缩聚焦**资源效率与成本优化**，生产化部署聚焦**全生命周期工程化管理**。本对比旨在厘清技术边界、明确适用条件，支撑开发者基于 SLA 要求、成本预算、交付节奏等维度做出理性选型。

## 关键维度对比表

| 维度 | 高并发推理（TPM 预留 / 快速模式） | 模型压缩 | 生产化部署（Model Production） |
|------|----------------------------------|----------|------------------------------|
| **核心目标** | 保障吞吐确定性（TPM 预留）或降低单请求延迟（快速模式） | 在可接受精度损失下，显著降低推理资源消耗（MU 规格）与单位推理成本 | 实现模型从训练到上线的端到端工程化交付：版本管理、弹性部署、环境隔离、可观测性 |
| **输入格式** | 标准 OpenAI 兼容 API 请求体（`/v1/chat/completions`），含 `model`、`messages`、`stream` 等字段；TPM 预留需使用专属 `model` code；快速模式需切换专属域名 | 百炼平台内已成功微调的自定义模型（状态为 `succeeded`），仅支持 `.bin` + `config.json` 格式；不支持基础模型或 OSS 导入模型 | 微调任务：`model_id` + `dataset_id` + `training_type`；部署任务：`fine_tuned_model_id` 或自有 Hugging Face 模型 ID + `deployment_config` |
| **输出格式** | 与标准 API 一致（JSON 响应），但快速模式额外返回 `reasoning_content` 字段（流式场景下分离推送）；TPM 预留无格式变更 | 输出为新模型 ID（如 `qwen3.5-flash-2026-02-23-quant`），可在部署环节作为 `model_id` 使用；不生成 API 响应 | 微调产出：`fine_tuned_model_id`；部署产出：`endpoint_url`（RESTful 推理地址）、`deployment_id`；API 响应格式同标准 `/v1/chat/completions` |
| **支持模型** | **TPM 预留**：千问、GLM、DeepSeek、Kimi 等主流模型多版本（北京/新加坡）；<br>**快速模式**：仅 `glm-5.2-fast-preview`（北京/新加坡） | 仅限百炼平台内完成的微调模型（如 `qwen3.5-flash-xxx`），不支持基础模型、第三方模型或 OSS 导入模型；仅北京地域可用 | **微调**：Qwen 系列等百炼基础模型（全参/LoRA）；Hugging Face 格式自定义模型（`bfloat16` + `config.json` + `pytorch_model.bin`）；<br>**部署**：所有微调产出模型、导入模型及部分基础模型 |
| **API 端点** | **TPM 预留**：复用标准域名 `https://dashscope.aliyuncs.com/...`，仅 `model` 参数替换为专属 code；<br>**快速模式**：专用域名 `https://{workspace_id}.cn-beijing.maas.aliyuncs.com/compatible-mode/v1`（北京）或对应新加坡域名 | 无独立 API；通过控制台界面或后台异步任务触发，结果以新模型 ID 形式体现 | 微调 API：`POST /api/v1/fine_tuning_jobs`；<br>部署 API：`POST /api/v1/deployments`；<br>推理端点：`POST {endpoint_url}/v1/chat/completions` |
| **计费方式** | **TPM 预留**：按预留 TPM 量（kTPM/月）预付费，超限可配置自动降级（按量计费）或拒绝；<br>**快速模式**：按 token 用量计费（当前 preview 阶段单价固定，不支持缓存折扣） | 压缩任务本身限时免费；压缩后模型的**部署费用按实际 MU 规格单独计费**（因规格降低而节省成本） | 微调：按 GPU 小时计费（A10/V100）；<br>部署：按 MU 实例规格 × 运行时长计费（支持弹性扩缩容）；<br>推理：按 token 用量计费（与标准 API 一致） |
| **典型场景** | - TPM 预留：高流量客服机器人、实时内容审核、金融风控批量分析（要求吞吐稳定、容忍短时延迟波动）<br>- 快速模式：AI 编程助手、Agent 多步推理链（首字节延迟敏感、需高 TPS） | 内部[知识库](../concepts/knowledge-base.md)问答、低频 but 高精度需求的垂直领域应用（如医疗报告生成）、边缘侧轻量部署（需严格控制 GPU 显存与成本） | - 新业务快速验证：dev/staging/prod 环境一键同步<br>- 多模型 A/B 测试与灰度发布<br>- 需要版本回滚、快照审计、资源隔离的企业级 SaaS 服务 |

## 各方案适用场景建议

- **选择高并发推理（TPM 预留 / 快速模式）当且仅当**：  
  ✅ 业务已具备稳定模型和成熟 API 调用逻辑，**当前瓶颈明确为性能（吞吐或延迟）**；  
  ✅ SLA 要求明确：如“99% 请求 TPM ≥ 50kTPM” 或 “P95 首字节延迟 < 200ms”；  
  ❌ 不适用于模型效果未达标、需频繁迭代训练、或尚未完成模型选型的早期阶段。

- **选择模型压缩当且仅当**：  
  ✅ 已完成微调并验证效果，**希望在不显著牺牲精度前提下降低推理成本**（尤其对 MU 规格敏感的中长尾业务）；  
  ✅ 部署环境资源受限（如预算有限、GPU 显存紧张），且能接受量化带来的轻微精度波动；  
  ❌ 不适用于基础模型直接部署、需持续微调的模型、或对精度零容忍的金融/医疗核心场景（需充分验证）。

- **选择生产化部署（Model Production）当且仅当**：  
  ✅ 需要**构建可重复、可审计、可运维的模型交付流水线**（非临时测试）；  
  ✅ 存在多环境（dev/staging/prod）、多版本、多团队协作需求；  
  ✅ 要求自动化扩缩容、健康监控、错误追踪等生产级能力；  
  ❌ 不适用于单次实验性调用、无需版本管理的 PoC 验证、或仅需静态文件托管的极简场景。

## 技术选型参考（面向开发者）

| 你的问题 | 推荐方案 | 关键依据 |
|----------|----------|----------|
| “我的 Qwen3.7 模型在促销期间突然流量激增，经常被限流，怎么办？” | ✅ **TPM 预留** | 直接锁定专属吞吐容量，解决公共资源池争抢问题；无需改模型、改代码，仅替换 `model` 参数即可生效。 |
| “Agent 应用每步推理都卡顿，用户等待感强，如何提速？” | ✅ **快速模式**（若模型匹配）<br>⚠️ 或结合 **TPM 预留 + 快速模式**（双保障） | 快速模式专为低延迟设计；若同时需容量保障，可为 `glm-5.2` 预留 TPM，并在其专属域名下调用 `glm-5.2-fast-preview`（注意：二者资源池物理隔离）。 |
| “微调后的模型部署要 4*A10，成本太高，能否压到 2*A10 还保持效果？” | ✅ **模型压缩** | 通过 PTQ 量化降低显存占用与计算强度，实测可减少 30%~50% MU 规格；务必用业务数据集验证压缩后效果。 |
| “我们有 5 个业务线，每个都要独立模型、独立环境、独立监控，怎么管？” | ✅ **生产化部署** | 提供原生的环境隔离（dev/staging/prod）、版本快照、弹性扩缩容策略，避免手动维护多套部署脚本。 |
| “刚训好一个 LoRA 模型，想立刻试用，但不想搭服务器” | ✅ **生产化部署**（快速部署）<br>➡️ 后续再叠加 **TPM 预留**（保障流量） | `POST /api/v1/deployments` 一键发布 endpoint；待流量上升后，再为该 endpoint 的模型申请 TPM 预留，实现演进式扩容。 |
| “需要把模型部署到客户私有云，且必须离线运行” | ❌ 三者均不适用<br>✅ 应选用 **百炼私有化部署方案** | 当前对比项均为公有云托管服务；私有化需单独申请，涉及镜像交付、License 绑定、离线推理引擎等。 |

> **重要提醒**：  
> - **组合使用是常态**：例如，“生产化部署”发布模型 → “模型压缩”优化资源 → “TPM 预留”保障大促流量；三者分属不同抽象层，协同而非互斥。  
> - **preview 功能谨慎评估**：快速模式处于 preview 阶段，其模型 ID、性能、计费可能调整，**不建议作为长期生产依赖**，仅用于性能探索或短期高优项目。  
> - **精度与成本的权衡**：模型压缩必然引入误差，务必在业务真实数据上做 A/B 测试，而非仅依赖通用 benchmark。  
> - **地域约束需前置检查**：TPM 预留（北京/新加坡）、模型压缩（仅北京）、生产化部署（全地域）——跨地域部署需规划数据与模型同步路径。
