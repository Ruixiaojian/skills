# 模型部署方式对比：高并发推理、模型压缩、模型监控

## 对比目的与背景

在百炼平台实际生产落地中，开发者常需在**性能、成本、可观测性**三者间进行权衡决策。高并发推理（TPM 预留 & 快速模式）聚焦于**服务交付能力优化**，解决流量高峰下的稳定性与实时性问题；模型压缩面向**资源效率提升**，通过量化降低部署开销；模型监控则构建**全链路可观测底座**，支撑故障诊断、成本治理与持续迭代。三者并非互斥替代方案，而是分属模型生命周期不同阶段（部署前优化 → 运行时保障 → 运行后治理）的关键能力。

本页旨在为开发者提供结构化选型参考：明确各方案的核心定位、能力边界、技术约束与适用场景，避免因误用或混用导致性能瓶颈、成本浪费或运维盲区。

## 关键维度对比表

| 维度 | 高并发推理（TPM 预留 / 快速模式） | 模型压缩 | 模型监控 |
|------|----------------------------------|----------|-----------|
| **核心目标** | 保障高吞吐/低延迟的稳定推理服务 | 降低自定义模型部署资源消耗与成本 | 实现模型调用全链路可观测与异常治理 |
| **输入格式** | 标准 API 请求（JSON，含 `model`、`messages`、`stream` 等） | 微调完成的自定义模型（状态为 `SUCCEEDED`） | 无显式输入；自动采集所有已开通监控的模型调用请求与响应 |
| **输出格式** | 标准流式/非流式响应（含 `usage`、`reasoning_content`（快速模式特有）等字段） | 新注册的压缩模型 ID（如 `my-qwen-ft-int4`），可直接用于部署 | 多维指标（RPM/TPM/TTFT/P99）、调用日志（含 input/output）、告警事件、Prometheus 时间序列数据 |
| **支持模型** | **TPM 预留**：千问、GLM、DeepSeek、Kimi 等主流基础模型及部分微调模型（按控制台列表）<br>**快速模式**：仅 `glm-5.2-fast-preview`（Preview 阶段） | **仅限百炼平台微调产出的自定义模型**（如 `qwen3.5-flash-2026-02-23`），不支持基础模型或第三方模型 | **普通监控**：所有可选模型（含基础模型、微调模型）<br>**高级监控/告警/推理日志**：仅北京、新加坡、弗吉尼亚地域模型（上海仅支持普通监控） |
| **API 端点** | **TPM 预留**：通用域名（`https://dashscope.aliyuncs.com/...`）+ 专属 model code<br>**快速模式**：专属 workspace 域名（`https://{workspace_id}.cn-beijing.maas.aliyuncs.com/...`）+ 固定 `-fast-preview` model ID | 无独立 API；通过控制台「模型压缩」页面触发异步任务，结果模型注册至模型中心后，使用标准部署/调用 API | 无调用型 API；提供 Prometheus 查询接口（`/api/v1/query_range`）及控制台可视化界面；日志需通过控制台或导出功能获取 |
| **计费方式** | **TPM 预留**：预付费（按天，kTPM） + 溢出 token 按量计费<br>**快速模式**：纯按 token 计费（输入/输出单价明确，缓存命中单独计价） | 压缩任务本身限时免费；**压缩后模型部署费用按 MU 规格（如 MU8）实时计费**，显著低于全精度模型 | 监控服务本身**免费**；但高级监控依赖云监控 Prometheus 实例（按实例规格与存储时长计费），推理日志存储产生 OSS 费用 |
| **典型场景** | - TPM 预留：电商大促期间客服机器人核心对话链路<br>- 快速模式：编程助手实时代码补全、Agent 多步推理首 [Token](../concepts/token.md) 响应 | 自研垂直领域模型（如金融风控、医疗问答）上线前资源优化，降低长期推理成本 | - 定位某次超时调用的根本原因（TTFT vs 吞吐瓶颈）<br>- 发现某 API Key 的异常高频调用（安全审计）<br>- 监控 [Token](../concepts/token.md) 消耗趋势，联动「免费额度用完即停」防超额 |

## 各方案适用场景建议

### ✅ 高并发推理（推荐组合使用）
- **必须启用 TPM 预留的场景**：  
  - 流量可预估且不可接受任何限流（如支付确认、订单生成等关键业务链路）；  
  - 需要刚性 SLA 保障（如合同约定 99.9% 可用性）；  
  - 多模型混合部署且需隔离资源（避免 A 模型突发流量挤占 B 模型容量）。  
- **优先考虑快速模式的场景**：  
  - 用户交互强、对首 [Token](../concepts/token.md) 延迟极度敏感（如 IDE [插件](../concepts/plugin.md)、实时语音转写后处理）；  
  - 流量波动剧烈但总量可控，愿以排队机制换取更高 TPS（而非硬性扩容）；  
  - 当前仅需 `glm-5.2` 且处于 Preview 验证期（**不建议用于生产核心链路**）。  
- **组合策略提示**：可先为基线模型（如 `glm-5.2`）创建 TPM 预留，再在其专属 model code 后缀追加 `-fast-preview`（需确认控制台支持），实现「容量保障 + 速度优化」双重目标。

### ✅ 模型压缩（推荐作为微调后必选环节）
- **强烈建议启用的场景**：  
  - 微调模型已通过效果验证，进入规模化部署阶段；  
  - 推理成本成为主要瓶颈（尤其长文本、高并发场景）；  
  - 对精度损失容忍度较高（如摘要、分类等任务），或已通过校准数据集验证量化后效果。  
- **禁用场景**：  
  - 模型仍在快速迭代中（压缩不可逆，无法继续微调）；  
  - 使用基础模型或导入模型（不支持压缩）；  
  - 地域为华北2以外（仅北京支持）。

### ✅ 模型监控（推荐全量开启，分级配置）
- **必须开启普通监控的场景**：  
  - 所有生产环境模型（用于用量统计、账单核对、免费额度管理）；  
  - 需基础失败率、RPM 趋势分析的日常运维。  
- **务必启用高级监控的场景**：  
  - 性能敏感型应用（需分钟级 TTFT/TPS 分析定位卡顿）；  
  - 需要请求/响应内容审计（合规审查、bad case 分析、数据回流训练）；  
  - 需设置自动化告警（如失败率 >5% 自动钉钉通知）；  
  - 已接入 Grafana 或自建可观测平台（依赖 Prometheus 数据源）。  
- **关键提醒**：  
  - **历史数据不可补录**——监控开通前的调用无记录，请尽早配置；  
  - 批量推理调用**不产生推理日志与细粒度性能指标**，仅计入用量统计。

## 技术选型参考（面向开发者）

| 选型问题 | 推荐决策路径 | 注意事项 |
|----------|--------------|----------|
| **“我的模型流量突增，频繁返回 429”** | ➤ 优先检查是否已开通 TPM 预留（而非仅依赖快速模式）<br>➤ 若未开通，立即创建 TPM 预留并切换至专属 model code<br>➤ 同时开启高级监控，确认是全局限流还是单模型瓶颈 | 快速模式**不解决 429 问题**（改排队而非拒绝），TPM 预留才是容量兜底方案 |
| **“微调模型部署成本过高，能否优化？”** | ➤ 确认模型为百炼微调产出且地域为北京<br>➤ 在控制台「模型压缩」页选择 MU8/MU16 等模板，搭配校准数据集<br>➤ 部署压缩模型并对比全精度版本的 P99 延迟与准确率 | 压缩后模型**不可逆、不可微调**，请务必在测试环境充分验证效果 |
| **“用户反馈某次回答很慢，但监控看平均延迟正常”** | ➤ 立即进入高级监控 → 日志页，用 Request ID 精确检索该次调用<br>➤ 查看 `model_first_token_duration`（TTFT）与 `model_call_duration_p99` 分离分析<br>➤ 结合 `protocol` 标签判断是否 SSE 流式传输导致前端渲染延迟 | 普通监控无单次日志，无法定位具体请求；务必开通「推理日志」 |
| **“如何防止某 API Key 被盗刷导致巨额账单？”** | ➤ 开启高级监控 + 告警<br>➤ 创建规则：`model_usage` 1 小时环比增长 >300% → CRITICAL 级别钉钉通知<br>➤ 同步启用「免费额度用完即停」开关作为最后一道防线 | 告警仅支持预设模板，无法自定义复杂条件（如多指标关联） |
| **“能否同时用 TPM 预留 + 快速模式 + 压缩模型？”** | ➤ 可行路径：`微调模型 → 压缩 → 为压缩后模型创建 TPM 预留 → （若支持）启用快速模式变体`<br>➤ 当前 `*-fast-preview` 仅支持基线模型，需关注文档更新 | 三者属于不同层级能力（部署层/模型层/观测层），**无本质冲突**，但需注意各能力的模型兼容性限制 |

> **最后建议**：将模型监控作为所有部署方案的「基础设施」先行开通；高并发推理与模型压缩按业务阶段渐进引入——初期用 TPM 预留保稳定，中期用模型压缩降成本，全程用监控驱动优化闭环。
